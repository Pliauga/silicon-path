Every program so far has spoken through `printf` in one direction only. This chapter opens the other direction: reading what the user types, without the program falling over. C gives you three standard streams and a handful of functions on top of them, and most beginner bugs here come from ignoring what one returned.

## Objectives

- Explain how `<stdio.h>` streams connect your program to the keyboard, the terminal and the error display.
- Read single characters with `getchar()` and write them with `putchar()`.
- Explain why `scanf("%d", &x)` needs the address-of operator, and why checking what it returns is mandatory.
- Use `fgets()` with `sscanf()` to read a line safely inside a fixed-size buffer.

## Why students struggle

`scanf` is a minefield, and the mines sit between how it looks and what it does. Writing `scanf("%d", x)` hands over the value of `x` rather than its address, so the parsed number lands wherever that value points: a crash, or silent corruption of some unrelated variable.

The second trap is quieter. Typing `500` and pressing Enter delivers four characters, and `scanf("%d", &x)` consumes the digits while leaving the newline in the stream, so the next `getchar()` or `fgets()` reads an empty line. A third waits in `scanf("%s", buf)`, which has no length limit and writes past the end of the array.

## The code, both ways

Both programs use three ideas: character output with `putchar`, checked parsing with `sscanf`, and stripping the newline a line buffer keeps. Neither reads the keyboard, because the input line is already a string.

### The money version

```c
// Money version (io_money.c)
#include <stdio.h>
#include <string.h>

int main(void) {
    // 1. Character I/O with putchar
    printf("Vault code prefix: ");
    putchar('G');
    putchar('B');
    putchar('\n');

    // 2. Safe formatted parsing from a line buffer (simulating fgets + sscanf)
    // In interactive code, you read 'line' with: fgets(line, sizeof(line), stdin)
    const char *rawInputLine = "Vance 14500\n";
    char holder[16];
    int depositPence = 0;

    // %15s limits string input to at most 15 chars + '\0' (prevents overflow!)
    // Always check that sscanf/scanf returns the expected number of matched items (2):
    int matched = sscanf(rawInputLine, "%15s %d", holder, &depositPence);
    if (matched == 2) {
        printf("Parsed %d fields -> Holder: %s, Deposit: %d pence (£%d.%02d)\n",
               matched, holder, depositPence,
               depositPence / 100, depositPence % 100);
    } else {
        fprintf(stderr, "Error: malformed bank deposit slip!\n");
    }

    // 3. Stripping the trailing '\n' that fgets keeps:
    char memo[32] = "Monthly ISA transfer\n";
    memo[strcspn(memo, "\n")] = '\0';   // replaces '\n' with '\0'
    printf("Cleaned memo: [%s]\n", memo);

    return 0;
}
```

    return 0;
}

### Compile and run

The same command compiles either program; only the file name changes.

```sh
cc -std=c17 -Wall -Wextra -Wpedantic -g io_money.c -o io_money
./io_money

cc -std=c17 -Wall -Wextra -Wpedantic -g io_football.c -o io_football
./io_football
```

| Name | What it does for you |
|---|---|
| `-std=c17` | Compiles against the ISO C17 standard, the version these programs target. |
| `-Wall -Wextra -Wpedantic` | Turns on the strict warnings that catch a missing `&` or a mismatched format specifier before you run anything. |
| `-g` | Keeps line numbers and variable information for a debugger. |
| `-o io_money` | Names the executable `io_money` instead of the default `a.out`. |

Each command writes an executable beside the source, so `./io_money` runs exactly that binary: the file changes only when you compile again. Every function used here is standard since C89, so `-std=c11` compiles both programs unchanged.

## What is really happening

A **stream** is an ordered sequence of bytes with a current position; `stdio.h` opens three before `main` runs. `stdin` is the keyboard, `stdout` the terminal's normal output, `stderr` its error output. `stdout` is buffered, so text can appear later than the write that produced it, while `stderr` is unbuffered: `fprintf(stderr, ...)` still reaches the terminal when `stdout` is redirected into a file.

`scanf` is a parser, not a line reader. It skips leading whitespace for every conversion except `%c` and `%[`, reads as many characters as the conversion allows, converts them, and stores the result **through the pointer you supplied**: that is why an `int` needs `&x` and a `char` array does not. It returns how many items were assigned, or `EOF` at end of input. That return value is the only reliable evidence the variable now holds something meaningful.

`getchar()` returns an `int` because it must report 256 byte values plus the sentinel `EOF`. `fgets(buf, n, stdin)` reads at most `n - 1` characters, stops after a newline, keeps it when it fits, and always terminates the buffer with a null byte; `sscanf` then parses the line you hold. Picture `stdin` as a conveyor belt: `scanf("%d", &x)` lifts the digits off the front and leaves the newline for the next reader.

| Function | Prototype or usage | Key behaviour |
|---|---|---|
| `getchar()` | `int ch = getchar();` | Reads one byte from `stdin`, or returns `EOF` (`-1`) at end of input. |
| `putchar(c)` | `putchar('A');` | Writes one character to `stdout`. |
| `printf(...)` | `printf("Val: %d\n", x);` | Formats and writes to `stdout`; returns the number of characters printed. |
| `scanf(...)` | `if (scanf("%d", &x) == 1)` | Skips leading whitespace for most specifiers except `%c`, parses input, returns the count of matched items, or `EOF`. |
| `fgets(buf, n, stdin)` | `if (fgets(buf, sizeof buf, stdin) != NULL)` | Reads at most `n - 1` characters, stopping at `'\n'`, **keeps `'\n'` if it fits**, and always appends `'\0'`. |

**Never use `gets()`.** It was removed from the C standard in C11 because it takes no buffer length, making overflow unavoidable. Use `fgets(buf, sizeof(buf), stdin)`, where size and buffer cannot drift apart.

## Where the analogy stops

The pneumatic tube is a lie in one detail. On a terminal, characters do not arrive one keystroke at a time: the operating system buffers a whole line inside the terminal driver until you press Enter. That is why a program in a `getchar()` loop seems to ignore you, and why the leftover newline is such a reliable trap. The stream is real, but delivery is a batch, not a trickle.

## Common mistakes

- **Forgetting `&` in `scanf("%d", x)`.** This passes the value of `x` as if it were an address, which segfaults immediately.
- **Unbounded `scanf("%s", buf)`.** A word longer than `sizeof(buf) - 1` overflows the array. Give the field a maximum width (`"%15s"` for `char buf[16]`) or use `fgets`.
- **Ignoring `scanf`'s return value.** When it fails on non-numeric input, `x` keeps its old or uninitialised value and the bad characters stay stuck in `stdin`.
- **Mixing `scanf("%d", ...)` with `fgets(...)` or `scanf("%c", ...)`.** Because `%d` leaves the newline in `stdin`, the next `fgets` returns an empty line; a leading space in `scanf(" %c", &ch)` skips it.
