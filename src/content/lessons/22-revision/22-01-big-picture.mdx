## Twenty-one lectures, one sentence

If the whole course compresses to a single claim, it is this: **C exposes the
machine, and the machine explains C.** Every awkward corner of the language —
why `int` overflow is undefined, why a struct has padding, why `volatile`
exists, why `malloc` does not return memory to the OS — stops being arbitrary
when you know what the hardware underneath is doing.

This lesson is not new material. It is the map, drawn at the end, so that the
individual lessons stop being a list and become a structure. Read it as a
revision aid: for each row of the table below, ask whether you could explain
the link without notes. The ones you cannot are the ones to reread.

## What you'll be able to do

- State the C construct → hardware concept link for each major topic.
- Explain why the link is causal, not a coincidence of curriculum design.
- Place any new C feature you meet onto this map.
- Identify which lectures you have not actually absorbed.

<TheoryBlock label="Why it matters for C" title="The map is the debugging method">

	When a C program misbehaves, the question "what does the machine think is
	happening" is almost always more productive than "what did I mean to write."
	A corrupted struct suggests alignment; a loop that never exits suggests a
	missing `volatile` or an overflow; a crash after `free` suggests a page
	mapping. The table below is that question, indexed.

## The map

| C construct | Hardware / OS concept | Lecture |
| --- | --- | --- |
| `char`, strings | ASCII and Unicode code points | 1 |
| `INT_MAX + 1` | two's complement, the sign bit | 2 |
| `struct` layout | byte alignment and machine words | 1, 3 |
| `&`, `|`, `^`, `~` | boolean algebra and gates | 4 |
| `++`, loops as state | latches, flip-flops, counters | 5 |
| pointers | the address space | 3 |
| `volatile` | caches, coherence, memory hierarchy | 6 |
| `malloc` / `free` | heap, virtual memory, page tables | 16, 17 |
| `fork()` | process = address space + PID | 11 |
| `pthread_create()` | threads share one address space | 12 |
| `pthread_mutex_lock()` | atomic instructions and wait queues | 14 |
| `fopen` / `fread` | I/O subsystem and buffering | 18 |
| `strcpy` into a small buffer | stack frame layout | 19 |
| `socket` / `htonl` | network byte order and the stack | 20 |

Three rows deserve the extra lecture numbers, because the same construct is
explained by two different levels. A struct's layout is decided by the word
size of the machine (lecture 1) *and* by the compiler's alignment rules for
that architecture (lecture 3). `malloc` asks the kernel for pages (lecture 16)
but what the process sees is virtual addresses the MMU translates (lecture 17).
The duplication is the point: there is no single level at which those
questions have an answer.

## The map, as data

The table above is a picture of an array. Writing it as one makes the structure
explicit and gives you something to extend when a lecture is missing.

```c
#include <stdio.h>
#include <string.h>

/* The curriculum on one page, as data rather than prose.
 *
 * Each row is a C construct, the hardware or OS concept that explains why it
 * behaves the way it does, and the lecture that covers the concept. The point
 * of printing it is that the table is derived from an array: add a row and
 * the table updates, which is the same argument as "make the mapping
 * explicit in code" one level up. */

struct link {
    const char *c_construct;
    const char *hardware;
    int lecture;
    const char *one_line;
};

static void rule(size_t width) {
    for (size_t i = 0; i < width; i++) putchar('-');
    putchar('\n');
}

int main(void) {
    const struct link links[] = {
        {"char c = 'A'",        "ASCII / Unicode",        1,
         "a char is a byte is a code point"},
        {"INT_MAX + 1",         "two's complement",        2,
         "wraps to INT_MIN; the sign bit is just a bit"},
        {"struct { char; int; }", "word alignment",        1,
         "padding makes it 8 bytes, not 5"},
        {"a & b, a | b, a ^ b", "boolean algebra",         4,
         "gate-level operations, applied 32 at a time"},
        {"int *p = &x",         "address space",           3,
         "a pointer is a typed address, nothing more"},
        {"volatile int flag",   "caches & coherence",      6,
         "forces a memory read the compiler would elide"},
        {"malloc(64)",          "heap & virtual memory",  16,
         "a mapping, not a pile of RAM"},
        {"free(p)",             "page tables",            17,
         "returns pages; the process keeps its VA"},
        {"fork()",              "process = address space", 11,
         "copy-on-write pages, separate PIDs"},
        {"pthread_create()",    "threads share an AS",    12,
         "same heap, same globals, own stack"},
        {"pthread_mutex_lock()", "atomic instructions",   14,
         "a lock is a CAS loop plus a wait queue"},
        {"fopen / fread",       "I/O subsystem, buffering", 18,
         "stdio buffers; the syscall is read(2)"},
        {"strcpy into char[8]", "stack frame layout",     19,
         "the return address is 8 bytes away"},
        {"socket / htonl",      "network byte order",     20,
         "big-endian on the wire, little on your CPU"},
    };
    const size_t count = sizeof links / sizeof links[0];

    printf("%-28s %-28s %-8s %s\n", "C construct", "hardware concept",
           "lecture", "why");
    rule(112);

    for (size_t i = 0; i < count; i++) {
        printf("%-28s %-28s L%-7d %s\n",
               links[i].c_construct,
               links[i].hardware,
               links[i].lecture,
               links[i].one_line);
    }

    /* A second view: how many rows point at each lecture. Not every lecture
     * appears, and the ones that appear twice are the ones where the C and
     * the hardware are hardest to separate. */
    printf("\nlectures referenced, counted:\n");
    for (int lec = 1; lec <= 22; lec++) {
        int n = 0;
        for (size_t i = 0; i < count; i++) {
            if (links[i].lecture == lec) n++;
        }
        if (n > 0) {
            printf("  L%-3d %d row(s)\n", lec, n);
        }
    }

    /* The through-line, in one sentence, checked for length. */
    const char *thesis =
        "C exposes the machine; the machine explains C.";
    printf("\nthesis (%zu chars): %s\n", strlen(thesis), thesis);

    return 0;
}
```

The count is the honest part of this exercise. Thirteen of twenty-two lectures
appear in a table of *the* central links. The rest — RISC versus CISC, pipelining,
scheduling, deadlock detection, thrashing, cloud service models — are real
material that a C program touches less directly. A revision map that claimed
every lecture had an equal footprint would be lying about the shape of the
subject.

## Which way the explanation runs

For each link, it is worth asking which direction the explanation goes.

| Link | Explanation runs | Because |
| --- | --- | --- |
| overflow → two's complement | hardware → C | the CPU's adder wraps; C inherits it |
| `volatile` → cache coherence | hardware → C | the compiler cannot see the cache |
| `malloc` → page tables | both ways | the API is C's; the cost is the MMU's |
| `fork()` → copy-on-write | OS → C | the semantics were chosen for the implementation |
| `strcpy` → stack layout | C → vulnerability | the language made the layout reachable |

Most arrows point from the machine to the language. Two do not, and they are
the interesting ones: `malloc`'s interface shapes what the allocator can do
with pages, and C's lack of bounds checking is what turns a stack layout into
an exploit class. The language is not purely downstream of the hardware; it
also decides which hardware facts become visible.

## Common pitfalls

### Treating the mapping as memorisation

Knowing that `volatile` relates to caches is not the same as knowing *when* to
use it: a variable modified by a signal handler or a memory-mapped register,
not a variable shared between threads (that needs atomics). The link is a
pointer to the reasoning, not the reasoning itself.

### Assuming one lecture per construct

Several constructs appear twice because they sit at a boundary — a struct is
both a byte layout and a compiler decision, an allocation is both an API and a
page mapping. That is a feature of the subject, not an inconsistency in the
notes.

### Revising by rereading

Rereading feels productive and is one of the weakest revision methods. The
program above is a better test: close the lesson, write the array from memory,
and see which rows you cannot fill. The gaps are the revision list.
