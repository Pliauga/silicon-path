## One queue or many

With two cores, a scheduler faces a choice the single-core case never raised:
is there one pool of ready processes, or one per core?

A **shared run queue** means whichever core goes idle takes the next process. It
balances load automatically and no core sits idle while work waits. The cost is
contention: every scheduling decision takes a lock on the shared queue, and the
queue becomes a hot cache line that bounces between cores.

**Per-core queues** eliminate that contention — each core owns its list and never
talks to the others. The cost is imbalance: if one core's queue holds long jobs
and another's holds short ones, the short core finishes early and idles while
work remains. That is where **work stealing** comes in: an idle core takes from
the back of another core's queue, which happens rarely enough to be cheap.

## What you'll be able to do

- Compare a shared run queue with per-core queues on contention and balance.
- Say what work stealing fixes and what it costs.
- Explain cache affinity and why it is a hint rather than a guarantee.
- Recognise false sharing and separate the hot fields that cause it.

## Two other effects

**Cache affinity.** A process that ran on core 0 has its data in core 0's cache.
Moving it to core 1 means refilling that cache — a cost measured in microseconds,
against a context switch measured in single-digit microseconds. Kernels therefore
try to keep a process on the core it last ran on, and only migrate for balance.

**False sharing.** Two threads write to different variables that happen to share
a 64-byte cache line. The hardware transfers the whole line back and forth, so
both threads slow down as though they shared one variable. The fix is padding:
put the hot values in separate cache lines. Module 6 covers the cache; this is
the case where it bites in a multithreaded program.

<TheoryBlock label="Why it matters for C" title="A thread's core is not stable, and your code must not care">

	Nothing in C promises which core a thread runs on, or that it stays there. `sched_setaffinity` can
	pin it, but pinning is a performance hint, not a correctness tool. If correctness depends on
	which core runs what, the code was wrong before it was pinned.
</TheoryBlock>

## Comparing the two arrangements

This is a model, not a measurement: it computes where each job would run under
each policy, with no real threads and no wall-clock time. That makes it
deterministic and lets you compare the two arrangements on identical work.

```c
#include <stdio.h>

/* Two cores, eight processes. Compare one global run queue against two
   per-core queues that each pull from the same list. Deterministic model:
   no real threads, just arithmetic on the scheduling decision.        */

#define CORES 2
#define COUNT 8

struct job {
    const char *name;
    int service;
};

/* Global run queue: whichever core is free takes the next job in order.
   This is what a modern kernel approximates with a shared run queue. */
static void global_queue(const struct job *jobs, int n) {
    int core_free[CORES] = { 0 };
    int total_wait = 0;
    int makespan = 0;

    printf("one shared run queue:\n");
    for (int i = 0; i < n; i++) {
        int core = 0;
        for (int c = 1; c < CORES; c++) {
            if (core_free[c] < core_free[core]) {
                core = c;               /* earliest free core wins */
            }
        }
        int start = core_free[core];
        int wait = start;               /* all jobs are ready at time 0 */
        core_free[core] = start + jobs[i].service;

        printf("  %-3s core %d  start %3d ms  finish %3d ms\n",
               jobs[i].name, core, start, core_free[core]);
        total_wait += wait;
    }

    for (int c = 0; c < CORES; c++) {
        if (core_free[c] > makespan) {
            makespan = core_free[c];
        }
    }
    printf("  average wait = %.1f ms, makespan = %d ms\n",
           (double)total_wait / n, makespan);
}

/* Per-core queues: deal the jobs out round robin, then each core runs its
   own list front to back. A core that finishes early sits idle.        */
static void per_core_queues(const struct job *jobs, int n) {
    int core_free[CORES] = { 0 };
    int total_wait = 0;
    int makespan = 0;

    printf("\ntwo per-core queues:\n");
    for (int i = 0; i < n; i++) {
        int core = i % CORES;
        int start = core_free[core];
        int wait = start;
        core_free[core] = start + jobs[i].service;

        printf("  %-3s core %d  start %3d ms  finish %3d ms\n",
               jobs[i].name, core, start, core_free[core]);
        total_wait += wait;
    }

    for (int c = 0; c < CORES; c++) {
        if (core_free[c] > makespan) {
            makespan = core_free[c];
        }
    }
    printf("  average wait = %.1f ms, makespan = %d ms\n",
           (double)total_wait / n, makespan);
}

int main(void) {
    const struct job jobs[COUNT] = {
        { "A", 7 }, { "B", 3 }, { "C", 9 },
        { "D", 2 }, { "E", 5 }, { "F", 8 },
        { "G", 1 }, { "H", 4 },
    };

    int total = 0;
    for (int i = 0; i < COUNT; i++) {
        printf("%s=%d ms  ", jobs[i].name, jobs[i].service);
        total += jobs[i].service;
    }
    printf("\ntotal work = %d ms on %d cores (perfect balance = %.1f ms)\n\n",
           total, CORES, (double)total / CORES);

    global_queue(jobs, COUNT);
    per_core_queues(jobs, COUNT);
    return 0;
}
```

Two numbers to compare. The shared queue finishes the batch in 20 ms; the split
queues take 22 ms, because core 0 ends up with 22 ms of work while core 1 has 17.
The perfect balance is 19.5 ms, so the shared queue is within 0.5 ms of ideal and
the split queues are 2.5 ms off.

On eight jobs that difference is noise. At eight thousand jobs it is the
difference between a batch finishing at 2 pm and at 4 pm — which is why work
stealing exists, and why "just give each core its own queue" is not the end of
the design.

## Common pitfalls

### Expecting per-core queues to balance themselves

Dealing jobs round robin only balances when the jobs are the same size. Here they
range from 1 to 9 ms, and the deal puts the four longest on core 0. Any static
split has this failure mode; only migration fixes it.

### Measuring makespan while ignoring when work becomes ready

Every job in this model is runnable at time 0. Real workloads have arrivals, and
a queue with nothing ready yet must not be counted as busy. Add an arrival field
and the "earliest free core" rule needs an idle check, or the model runs jobs
before they exist.

### Assuming a process stays on one core

Cache affinity is a preference, not a guarantee. A program that is correct only
when a thread stays on one core is incorrect on every real system, because the
kernel will migrate it the moment balance demands it.

### Forgetting false sharing on adjacent variables

Two `int` counters declared next to each other land in the same cache line. Two
threads incrementing them serialize on the cache coherency protocol despite
touching different memory. The symptom is a program that does not scale past one
core for no visible reason; the fix is a 64-byte pad between the hot fields.
