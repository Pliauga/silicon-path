## A file descriptor that happens to be a network

The sockets API is the operating system's interface to the network stack, and
its most important design decision is that a socket is a file descriptor. It
appears in the same table as open files, it is closed with the same `close()`,
and on Unix you can `read()` and `write()` to it as if it were a file. That
unification is why `select()` can wait on files and sockets together and why
`ssh` can pipe its output into anything.

The differences appear as soon as you look closely. A file's reads return the
bytes you asked for or end-of-file; a socket's reads return whatever has
arrived, which might be half a message. A file's `write` either works or fails;
a socket's `write` accepts bytes into a kernel buffer and promises nothing
about delivery. Network code is the discipline of handling those differences
without pretending they are not there.

## What you'll be able to do

- Name the calls a TCP server makes, in order, and what each one allocates.
- Convert between host and network byte order and say why it is needed.
- Write the address-parsing half of a client with `inet_pton` and `htons`.
- Explain why `send()` returning the byte count is not a delivery receipt.

## The call sequence

The server calls are in a fixed order, and each one has a failure mode that
produces a different errno.

| Call | Purpose | Fails with |
| --- | --- | --- |
| `getaddrinfo` | resolve a name to a list of address candidates | `EAI_NONAME` |
| `socket` | allocate an endpoint, get a descriptor | `EMFILE` (out of fds) |
| `bind` | claim a local address and port | `EADDRINUSE` |
| `listen` | mark it as accepting, set the backlog | `EOPNOTSUPP` |
| `accept` | block until a peer connects, return a **new** fd | `EINTR` |
| `read`/`write` | exchange bytes on the accepted fd | `EPIPE` |
| `close` | release both descriptors | — |

`accept` returning a new descriptor is the part people miss. The listening
socket is not for data; it exists only to produce connected sockets, one per
peer. A server with 1,000 clients has 1,001 descriptors open.

Client side, `socket` then `connect`, with `bind` usually omitted because the
kernel picks an ephemeral port. `getaddrinfo` is preferred over the older
`gethostbyname` because it handles both IPv4 and IPv6 and returns a linked list
you can try in order.

## The sequence, not run

This is a correct TCP server skeleton. It is a fenced block, not a compiled
program, because there is no port to listen on here.

```c
/* Requires a live port and a client to connect. Not executed in this lesson. */
#define _POSIX_C_SOURCE 200809L
#include <netdb.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <unistd.h>

int serve(const char *port) {
    struct addrinfo hints;
    struct addrinfo *res = NULL;

    memset(&hints, 0, sizeof hints);
    hints.ai_family = AF_UNSPEC;      /* v4 or v6 */
    hints.ai_socktype = SOCK_STREAM;  /* TCP, not UDP */
    hints.ai_flags = AI_PASSIVE;      /* bind to any local address */

    int rc = getaddrinfo(NULL, port, &hints, &res);
    if (rc != 0) {
        fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc));
        return -1;
    }

    int listen_fd = -1;
    for (struct addrinfo *p = res; p != NULL; p = p->ai_next) {
        listen_fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
        if (listen_fd < 0) continue;

        int yes = 1;
        /* Without this, restarting the server fails with EADDRINUSE for
           up to two minutes while old connections sit in TIME_WAIT. */
        setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof yes);

        if (bind(listen_fd, p->ai_addr, p->ai_addrlen) == 0) break;

        close(listen_fd);
        listen_fd = -1;
    }
    freeaddrinfo(res);

    if (listen_fd < 0) {
        fprintf(stderr, "could not bind\n");
        return -1;
    }
    if (listen(listen_fd, 16) != 0) {
        perror("listen");
        close(listen_fd);
        return -1;
    }

    for (;;) {
        struct sockaddr_storage peer;
        socklen_t peer_len = sizeof peer;

        int conn_fd = accept(listen_fd, (struct sockaddr *)&peer, &peer_len);
        if (conn_fd < 0) continue;    /* EINTR is normal, just retry */

        /* read() may return fewer bytes than requested. A TCP stream has
           no message boundaries, so the application must frame its data. */
        char buf[512];
        ssize_t n = read(conn_fd, buf, sizeof buf);
        if (n > 0) {
            ssize_t sent = 0;
            while (sent < n) {
                ssize_t w = write(conn_fd, buf + sent, (size_t)(n - sent));
                if (w <= 0) break;
                sent += w;
            }
        }
        close(conn_fd);               /* the connected socket, not the listener */
    }
}
```

Two lines in that skeleton are worth memorising. `SO_REUSEADDR` prevents the
most common "my server won't restart" confusion, and the `while (sent < n)`
loop exists because `write` on a socket may accept only part of what you gave
it. A single un-looped `write` is a bug that appears under load and nowhere
else.

## Byte order, which you can test offline

The address you type is text. The address in a socket struct is a 32-bit
integer in **network byte order** — big-endian, by convention. The integer your
CPU does arithmetic on is in **host byte order**, which on x86 and ARM is
little-endian. `htonl` and `ntohl` convert; forgetting them is the classic first
networking bug, and it does not produce an error, it produces a connection to
`1.0.168.192`.

```c
#include <arpa/inet.h>
#include <netinet/in.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>

/* Offline half of socket programming: text address -> 32-bit address, and
 * host order <-> network order. No socket is opened, no port is bound.
 *
 * The point is the byte order. A socket address in memory holds the address
 * in network order (big-endian), while the integer you do arithmetic on is
 * in host order (little-endian on x86 and ARM by default). htonl and ntohl
 * are the conversion, and forgetting them is the classic first-network-bug. */

union addr_view {
    uint32_t word;
    unsigned char bytes[4];
};

static void show_bitmap(const char *label, uint32_t network_order) {
    const unsigned char *b = (const unsigned char *)&network_order;
    printf("%-22s", label);
    for (int i = 0; i < 4; i++) {
        printf("%02x", b[i]);
        if (i != 3) printf(":");
    }
    printf("\n");
}

int main(void) {
    const char *texts[] = {"192.168.0.1", "10.0.0.255", "127.0.0.1", "0.0.0.0"};
    const size_t count = sizeof texts / sizeof texts[0];

    printf("%-14s %-12s %-12s %s\n", "dotted quad", "host order", "net order",
           "as 4 bytes in memory");
    printf("%-14s %-12s %-12s %s\n", "-----------", "----------", "---------",
           "-------------------");

    union addr_view v;
    for (size_t i = 0; i < count; i++) {
        struct in_addr a;
        if (inet_pton(AF_INET, texts[i], &a) != 1) {
            printf("%-14s rejected by inet_pton\n", texts[i]);
            continue;
        }
        uint32_t net = a.s_addr;              /* already network order */
        uint32_t host = ntohl(net);           /* network -> host */

        v.word = host;
        printf("%-14s 0x%08x   0x%08x   %02x.%02x.%02x.%02x\n",
               texts[i], host, net,
               v.bytes[0], v.bytes[1], v.bytes[2], v.bytes[3]);
    }

    /* Why htonl matters: the same integer, two orders, two different byte
     * sequences. A socket address field expects the right one. */
    uint32_t value = 0xc0a80001u;             /* 192.168.0.1, host order */
    printf("\nsame integer 0x%08x written two ways:\n", value);
    show_bitmap("host order bytes:", value);
    show_bitmap("network (htonl):", htonl(value));

    /* Round trip: a client fills sin_addr with htonl, a server reads it
     * back with ntohl. These must agree or the connection goes nowhere. */
    uint32_t sent = htonl(value);
    uint32_t received = ntohl(sent);
    printf("\nsent 0x%08x -> on the wire 0x%08x -> read back 0x%08x\n",
           value, sent, received);
    printf("round trip intact: %s\n", received == value ? "yes" : "no");

    /* The port lives in the same struct and needs the same treatment. */
    uint16_t port = 8080;
    uint16_t port_net = htons(port);
    printf("\nport %u -> network 0x%04x -> back %u\n",
           (unsigned)port, (unsigned)port_net, (unsigned)ntohs(port_net));

    /* A struct sockaddr_in is 16 bytes: family, port, address, padding. */
    struct sockaddr_in sa;
    memset(&sa, 0, sizeof sa);
    sa.sin_family = AF_INET;
    sa.sin_port = htons(443);
    sa.sin_addr.s_addr = htonl(value);

    /* Only sin_addr's offset is portable here: macOS puts a one-byte
       sin_len before sin_family, Linux does not, so the earlier fields
       shift by one between the two. sin_addr lands at 4 either way. */
    printf("\nstruct sockaddr_in is %zu bytes\n", sizeof sa);
    printf("  sin_addr at offset %zu on this platform\n",
           offsetof(struct sockaddr_in, sin_addr));

    /* Inet_ntop is the inverse of inet_pton: bytes back to text. */
    char back[INET_ADDRSTRLEN];
    if (inet_ntop(AF_INET, &sa.sin_addr, back, sizeof back) != NULL) {
        printf("\ninet_ntop of the struct: %s\n", back);
    }

    return 0;
}
```

## Expected output

```text
dotted quad    host order   net order    as 4 bytes in memory
-----------    ----------   ---------    -------------------
192.168.0.1    0xc0a80001   0x0100a8c0   01.00.a8.c0
10.0.0.255     0x0a0000ff   0xff00000a   ff.00.00.0a
127.0.0.1      0x7f000001   0x0100007f   01.00.00.7f
0.0.0.0        0x00000000   0x00000000   00.00.00.00

same integer 0xc0a80001 written two ways:
host order bytes:     01:00:a8:c0
network (htonl):      c0:a8:00:01

sent 0xc0a80001 -> on the wire 0x0100a8c0 -> read back 0xc0a80001
round trip intact: yes

port 8080 -> network 0x901f -> back 8080

struct sockaddr_in is 16 bytes
  sin_addr at offset 4 on this platform

inet_ntop of the struct: 192.168.0.1
```

Read the first table's last two columns against each other. The host-order
value of `192.168.0.1` is `0xc0a80001` — readable as four decimal bytes. The
network-order value is `0x0100a8c0`, which looks like nonsense until you
realise it is the same four bytes in the other order, and that the memory
dump `01.00.a8.c0` is exactly the byte sequence that goes on the wire.

The final line is the round trip that matters: `inet_pton` writes network
order, `inet_ntop` reads it back, and the text survives. A server that skipped
`ntohl` would build a `sockaddr_in` whose bytes are reversed, and `connect`
would fail or, worse, reach a different machine.

## Common pitfalls

### Assuming one `read` is one message

TCP is a byte stream. Two `write`s of 100 bytes can arrive as one 200-byte
`read`, or as three reads of 60, 60, and 80. Boundaries are the application's
job — length prefixes, delimiters, or a fixed-size header. Code that assumes
otherwise works on localhost and fails on the first real network.

### Ignoring short writes

`sent = write(fd, buf, n)` returning less than `n` is legal and common when the
socket buffer is full. Loop until every byte is accepted, as the skeleton does.
The same applies to `send` with `MSG_NOSIGNAL` to avoid `SIGPIPE` killing the
process when the peer has gone.

### Leaving `SIGPIPE` at its default

Writing to a socket whose peer closed raises `SIGPIPE`, and the default action
is to terminate the process. A server that survives client disconnects sets
`SIG_IGN` or uses `MSG_NOSIGNAL`. Discovering this in production is a rite of
passage best skipped.

### Using `inet_addr` instead of `inet_pton`

`inet_addr` returns `INADDR_NONE` (`0xffffffff`) both for errors and for the
valid broadcast address `255.255.255.255`, so the two are indistinguishable.
`inet_pton` returns 1, 0, or -1 and has no ambiguity. It also has an IPv6
sibling with the same signature.

## Ports and descriptors, briefly

| Range | Use |
| --- | --- |
| 0–1023 | well-known; binding needs privilege on Unix |
| 1024–49151 | registered; servers usually live here |
| 49152–65535 | ephemeral; the kernel picks these for clients |

A client that connects without calling `bind` gets an ephemeral port chosen by
the kernel, and that port stays associated with the connection until it closes.
This is why a machine making many short-lived connections can exhaust its
ephemeral range — the connections sit in `TIME_WAIT` for twice the maximum
segment lifetime after closing.
