## Why anyone bothered with seven layers

Sending a byte from one machine to another involves radio waves, copper,
switching hardware, routing tables, retransmission timers, and an application
that wants a web page. Each of those concerns is wildly different, and each
changes on a different schedule: a new Wi-Fi standard appears every few years,
while HTTP/1.1 lasted fifteen.

The OSI model is a claim that these concerns can be separated. If each layer
offers a service and demands only that service from the layer below, then
changing how fibre encodes bits does not require changing a mail client. The
model was published by ISO in 1984 as a *reference* — a vocabulary for arguing
about where a function belongs — and it never shipped as a working stack. The
protocols that did ship, TCP/IP, collapse it into four layers. The seven-layer
vocabulary survived anyway, because it is the most useful thing in the room for
asking "whose bug is this?"

## What you'll be able to do

- Name the seven layers in order and give a device or protocol at each.
- Say what a layer adds to the data it receives from the layer above.
- Use the model to localise a fault: cable, address, port, or application.
- Explain why TCP/IP has four layers and OSI has seven.

## The seven layers

| # | Layer | Unit | Job | Examples |
| --- | --- | --- | --- | --- |
| 7 | Application | data | what the user asked for | HTTP, DNS, SMTP |
| 6 | Presentation | data | encoding, compression, encryption | TLS, UTF-8, JPEG |
| 5 | Session | data | dialogue state, checkpoints | RPC, sockets API |
| 4 | Transport | segment | end-to-end delivery, ports | TCP, UDP |
| 3 | Network | packet | addressing and routing across networks | IP, ICMP |
| 2 | Data link | frame | framing on one link, MAC addresses | Ethernet, Wi-Fi |
| 1 | Physical | bits | voltage, light, radio | 1000BASE-T, 802.11 PHY |

Read it bottom-up to see the accumulation. Layer 1 moves a bit. Layer 2 groups
bits into a frame with a header carrying a hardware address, so a frame can
reach the right device on one wire. Layer 3 adds a logical address that survives
crossing many wires, so a packet can be routed anywhere. Layer 4 adds ports so
that many conversations can share one host. Layer 7 is the request itself.

Each layer's header is opaque to the layer below. That is the entire trick, and
it is the same trick as an abstract data type: the lower layer sees bytes to
move and knows nothing about what they mean.

<TheoryBlock label="Why it matters for C" title="Encapsulation is a struct with a payload">

	Layer 2 receiving layer 3's output is doing exactly what a function that
	takes `const void *data, size_t len` does — moving an opaque blob. When you
	write a network client you will hand the kernel a buffer and a length, and
	every header below yours will be prepended by code you never call directly.
	Understanding the model is understanding which of those prepends your program
	is responsible for, and which the kernel does on your behalf.

</TheoryBlock>

## Where the model earns its keep

A user says "the site is down." The model turns that into a sequence of
questions with different answers and different owners.

| Question | Layer | If it fails |
| --- | --- | --- |
| Is the cable/radio up? | 1 | link light off, interface `NO-CARRIER` |
| Does ARP resolve the gateway? | 2 | frames sent, nothing replies |
| Can I ping the server's IP? | 3 | routing or firewall |
| Does the port accept a connection? | 4 | service not listening, or blocked |
| Does the app answer correctly? | 7 | the server is fine; the request is wrong |

The value is that these are checked in order and each one narrows the search.
Skipping to layer 7 and reading logs is how a two-minute cable problem becomes
an afternoon.

## The four-layer reality

TCP/IP maps onto OSI unevenly, and the unevenness is instructive:

| OSI | TCP/IP | Note |
| --- | --- | --- |
| 7, 6, 5 | Application | merged; TLS sits inside it |
| 4 | Transport | TCP and UDP |
| 3 | Internet | IP |
| 2, 1 | Link | Ethernet, Wi-Fi, drivers |

The merge of 5, 6, and 7 was not laziness. In practice session state,
encoding, and the application protocol are so entangled — think HTTP cookies
and content encoding — that a boundary between them was never enforceable. The
model's seven layers are a checklist of *concerns*; the deployed stack is a
checklist of *interfaces*. Four interfaces is what survived contact with
implementations.

## The model, as data

The table above is easier to trust when a program produces it. This one stores
the seven layers as an array, sorts them with `qsort` — a comparison function
pointer is the one C feature the layer diagram never mentions — and then costs
out encapsulation: how much of a packet is header and how much is the request.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* The model as data, so the table in the lesson and the program agree.
 *
 * Two things happen here. First the seven layers are sorted by number with
 * qsort, which is the one place in this curriculum where a comparison
 * function pointer shows up. Second, a protocol name is mapped back to its
 * layer by linear search — the operation you actually perform when a packet
 * is misbehaving and you need to know whose bug it is. */

struct layer {
    int number;
    const char *name;
    const char *unit;
    const char *example;
};

static int by_number(const void *a, const void *b) {
    const struct layer *la = a;
    const struct layer *lb = b;
    return (la->number > lb->number) - (la->number < lb->number);
}

static const char *layer_of(const char *protocol) {
    static const struct {
        const char *name;
        int layer;
    } known[] = {
        {"HTTP", 7}, {"DNS", 7}, {"SMTP", 7},
        {"TLS", 6}, {"UTF-8", 6},
        {"sockets", 5},
        {"TCP", 4}, {"UDP", 4},
        {"IP", 3}, {"ICMP", 3},
        {"Ethernet", 2}, {"Wi-Fi", 2},
        {"1000BASE-T", 1},
    };

    for (size_t i = 0; i < sizeof known / sizeof known[0]; i++) {
        if (strcmp(known[i].name, protocol) == 0) {
            static char buf[32];
            snprintf(buf, sizeof buf, "layer %d", known[i].layer);
            return buf;
        }
    }
    return "unknown";
}

int main(void) {
    struct layer layers[] = {
        {4, "Transport",  "segment", "TCP, UDP"},
        {7, "Application", "data",   "HTTP, DNS, SMTP"},
        {1, "Physical",   "bit",     "1000BASE-T, 802.11 PHY"},
        {6, "Presentation", "data",  "TLS, UTF-8, JPEG"},
        {3, "Network",    "packet",  "IP, ICMP"},
        {5, "Session",    "data",    "RPC, sockets API"},
        {2, "Data link",  "frame",   "Ethernet, Wi-Fi"},
    };
    const size_t count = sizeof layers / sizeof layers[0];

    printf("as declared: ");
    for (size_t i = 0; i < count; i++) {
        printf("%d%s", layers[i].number, i + 1 < count ? ", " : "\n");
    }

    qsort(layers, count, sizeof layers[0], by_number);

    printf("after qsort: ");
    for (size_t i = 0; i < count; i++) {
        printf("%d%s", layers[i].number, i + 1 < count ? ", " : "\n");
    }

    printf("\n%-3s %-14s %-9s %s\n", "#", "layer", "unit", "examples");
    for (size_t i = 0; i < count; i++) {
        printf("%-3d %-14s %-9s %s\n",
               layers[i].number, layers[i].name,
               layers[i].unit, layers[i].example);
    }

    /* Each layer adds a header and hands the result down. The size grows by
     * a fixed amount per layer; this is the encapsulation the prose claims. */
    printf("\nencapsulation of a 100-byte request:\n");
    int size = 100;
    printf("  application payload        %4d bytes\n", size);
    size += 20; printf("  + TCP header (20)          %4d bytes\n", size);
    size += 20; printf("  + IP header (20)           %4d bytes\n", size);
    size += 14; printf("  + Ethernet header (14)     %4d bytes\n", size);
    size += 4;  printf("  + Ethernet FCS (4)         %4d bytes\n", size);
    printf("  overhead %d bytes, %.0f%% of what was sent\n",
           size - 100, ((size - 100) * 100.0) / size);

    printf("\nprotocol lookup:\n");
    const char *probes[] = {"HTTP", "TCP", "IP", "Ethernet", "COBOL", NULL};
    for (size_t i = 0; probes[i] != NULL; i++) {
        printf("  %-12s -> %s\n", probes[i], layer_of(probes[i]));
    }

    return 0;
}
```

```text
  TCP          -> layer 4
  IP           -> layer 3
  Ethernet     -> layer 2

```

The encapsulation arithmetic is the part to sit with. A 100-byte request leaves
the machine as 158 bytes, so 37% of what crossed the wire was headers. That
fraction is why IPv6 dropped optional fields from the fixed header, why TCP
selective acknowledgement exists, and why a request with a 20-byte payload over
TCP/IPv4/Ethernet is mostly overhead. It is also why the layers are worth
separating: each header is added by code that does not know or care what the
one above it meant.

## Common pitfalls

### Treating the layers as physical

Nothing in a running system corresponds to "layer 5." The layers are a way of
partitioning responsibility in an argument, not a set of processes. A single
`send()` call in your C program traverses all of them inside the kernel and
returns a count.

### Believing each layer is a separate program

The lower layers live in the kernel and the network card. A user program
touches layer 4 through the sockets API and layer 7 through whatever protocol
it implements. Layers 1–3 are someone else's code, which is exactly why the
interfaces between them are standardised.

### Assuming OSI order describes time

The headers are added on the way down at the sender and removed on the way up
at the receiver, but the receiver's layers do not run in lockstep. A frame can
be parsed by hardware, queued, and handed up later. Ordering of *layers* is
not ordering of *instants*.
