## Rules you can check by exhaustion

Boolean algebra is arithmetic over the two values `0` and `1`, with
`AND`, `OR`, and `NOT` playing the roles of multiply, add, and negate.
Its laws look obvious because the domain is so small — and that is also
what makes them checkable. There are only four input combinations for two
variables, so any identity over two variables can be verified completely
by trying all of them.

The most useful law is **De Morgan's**:

- `~(a & b)` equals `~a | ~b`
- `~(a | b)` equals `~a & ~b`

In words: negating a compound condition flips the operator and negates
each part. This is not a memorised trick. It is the reason a compiler can
turn `if (!(x && y))` into a branch on `!x || !y` — and the reason you can
rewrite a condition to be readable without changing its meaning.

## What you'll be able to do

- State De Morgan's two laws and apply them to a C condition without error.
- Verify an identity by exhaustive enumeration over a byte.
- Simplify a condition using the distributive and absorption laws.
- Explain why `!(a && b)` is not `!a && !b`.

## The laws that matter

| Law | AND form | OR form |
| --- | -------- | ------- |
| Identity | `a & 1 == a` | `a \| 0 == a` |
| Annihilation | `a & 0 == 0` | `a \| 1 == 1` |
| Idempotence | `a & a == a` | `a \| a == a` |
| Complement | `a & ~a == 0` | `a \| ~a == 0xFF` |
| Commutative | `a & b == b & a` | `a \| b == b \| a` |
| Associative | `(a & b) & c == a & (b & c)` | `(a \| b) \| c == a \| (b \| c)` |
| Distributive | `a & (b \| c) == (a & b) \| (a & c)` | `a \| (b & c) == (a \| b) & (a \| c)` |
| Absorption | `a & (a \| b) == a` | `a \| (a & b) == a` |
| De Morgan | `~(a & b) == ~a \| ~b` | `~(a \| b) == ~a & ~b` |

Two of these are worth pausing on because they surprise people coming
from ordinary arithmetic.

**Distributive works both ways.** In normal algebra, `a × (b + c)` expands
but `a + (b × c)` does not factor. In Boolean algebra both directions
hold, because the domain has only two values. That is what makes
sum-of-products and product-of-sums both valid ways to build a circuit.

**Absorption has no arithmetic analogue.** `a | (a & b) == a` says that
if `a` is already true, the extra term cannot change the answer. This is
the law that lets you delete terms during simplification, and it is the
one beginners skip.

	`if (!(a && b))` and `if (!a || !b)` are identical. The second is usually

	"neither", which is a real and common bug in validation code: rejecting
	input when *both* fields are missing instead of when *either* is.

## Checking a law rather than trusting it

A law over one byte has 256 values; over two bytes, 65,536 pairs. That is
small enough to test completely, and doing so turns a memorised rule into
a measured fact.

The program below runs both De Morgan identities over every pair of byte
values and counts how many times each holds. It then shows the same law
in its comparison form, where it actually gets used.

```c
#include <stdint.h>
#include <stdio.h>

/* De Morgan's laws, checked over every pair of byte values.
 * If either identity ever failed, the count would be below 65536. */

int main(void) {
    int first = 0;
    int second = 0;

    for (unsigned a = 0; a < 256u; a++) {
        for (unsigned b = 0; b < 256u; b++) {
            first  += (~(a & b) & 0xFFu) == ((~a | ~b) & 0xFFu);
            second += (~(a | b) & 0xFFu) == ((~a & ~b) & 0xFFu);
        }
    }

    printf("~ (a & b) == ~a | ~b   for %d of 65536 pairs\n", first);
    printf("~ (a | b) == ~a & ~b   for %d of 65536 pairs\n\n", second);

    /* The same laws in their comparison form, which is where they are
     * actually useful: negating a compound condition. */
    int age = 20;
    int has_ticket = 0;

    printf("if (!(age >= 18 && has_ticket)) -> %s\n",
           (!(age >= 18 && has_ticket)) ? "true" : "false");
    printf("if (age < 18 || !has_ticket)    -> %s\n",
           (age < 18 || !has_ticket) ? "true" : "false");
    return 0;
}
```

## Expected output

```text
~ (a & b) == ~a | ~b   for 65536 of 65536 pairs
~ (a | b) == ~a & ~b   for 65536 of 65536 pairs

if (!(age >= 18 && has_ticket)) -> true
if (age < 18 || !has_ticket)    -> true
```

Both counts are total. That is exhaustive proof for eight-bit values: no
pair was left untested, so no counterexample exists at this width. The
same argument extends to wider types because the law acts on each bit
independently, but the code does not prove that part — the algebra does.

The two conditions at the bottom are the payoff. `age` is 20, so the first
half of the conjunction is true; `has_ticket` is 0, so the whole
conjunction is false and its negation is true. The rewritten form reaches
the same answer through a path a reader can follow: either under-age, or
without a ticket.

Note the transformation of the comparison as well as the connectives.
`!(age >= 18)` becomes `age < 18`. Negating a comparison flips it, and
forgetting that step is the usual way a De Morgan rewrite goes wrong.

## Simplifying a real condition

Start with something written defensively:

```c
if ((admin || owner) && (admin || editor)) { /* ... */ }
```

Factor out `admin` using the OR-distributive law:

```c
if (admin || (owner && editor)) { /* ... */ }
```

That is fewer operations and, more importantly, states the rule: admins
always pass; everyone else needs both roles. The compiler will optimise
either version into similar instructions, so the reason to simplify is
readability, not speed.

## Common pitfalls

### Writing `!a && !b` for `!(a && b)`

This is the canonical error. `!(a && b)` is true when *either* is false;
`!a && !b` is true only when *both* are false. De Morgan's law has the
`&&` become `||`, and dropping that flip changes the meaning.

### Forgetting to negate the comparison

`!(x > 5)` is `x <= 5`, not `x < 5`. The negation of a strict inequality
is a non-strict one in the other direction, and the boundary case at
exactly 5 is where bugs live.

### Applying bitwise laws to `&&`

`a & (b | c) == (a & b) | (a & c)` holds for bits. `a && (b || c)`
short-circuits: if `a` is false, `b` and `c` are never evaluated. That is
observable when they have side effects, and it is why the two operators
are not interchangeable even when the truth values coincide.

### Assuming the compiler preserves your grouping

Boolean expressions have no sequencing in the algebra. `&&` and `||` do
short-circuit by definition, but `&` and `|` do not, and a compiler may
reassociate them freely. If the order of side effects matters, split the
expression into separate statements.
