## The device is an address

There are two ways to talk to hardware. **Port-mapped I/O** gives devices
their own separate address space and their own instructions — x86 does
this with `in` and `out`. **Memory-mapped I/O** gives devices ordinary
addresses in the same space as memory, so a device register is read and
written with the same `load` and `store` instructions as an `int`.

Memory-mapped I/O won. It needs no new instructions, no new addressing
mode, and no special case in the compiler. A pointer to a device is
typed exactly like a pointer to an array, and the only difference is that
the address does not point at RAM.

## What you'll be able to do

- Explain why memory-mapped I/O needs no new CPU instructions.
- Read and write a device through a `volatile` pointer.
- Say why the register offsets are part of a hardware contract.
- Recognise the alignment requirement of a 32-bit register.

## A window, not a region

A device occupies a small range of addresses — usually a few dozen bytes
— placed somewhere in the physical address map. The CPU writes to
`base + 0x00` to transmit and reads `base + 0x04` to check status. Those
offsets are not an implementation detail; they are the interface, fixed
by the hardware designer and printed in the datasheet.

| Offset | Name      | Access | Meaning               |
| ------ | --------- | ------ | --------------------- |
| +0x00  | TX        | write  | byte to transmit      |
| +0x04  | STATUS    | read   | bit 0 = busy          |
| +0x08  | ID        | read   | device identifier     |

Notice that `ID` is read-only and returns a constant the device supplies.
It looks like a variable that never changes, and the compiler would be
delighted to fold it away. That is why every access goes through a
pointer.

<TheoryBlock label="Why it matters for C" title="volatile is a promise about reads, not about threads">

	`volatile` tells the compiler that every read and every write in the
	source must appear in the generated code, in that order, and may not be
	cached, folded, or reordered with other volatile accesses. It does not
	make an operation atomic and it does not synchronise threads. C11 gives
	you `_Atomic` and `<stdatomic.h>` for that, and they are a different
	tool. Using `volatile` for thread sharing is the single most common
	misuse of the keyword.
</TheoryBlock>

## A device in an array

The program below puts a device window inside a plain byte array. The
`reg` helper does the one thing that matters: it casts an address to
`volatile uint32_t *` so the compiler emits a real load or store every
time.

```c
#include <stdint.h>
#include <stdio.h>

/* Memory-mapped I/O: the device is not a function you call, it is an
 * address you read and write. Here the "hardware" is a byte array, and
 * the register offsets are the contract. */

#define MMIO_BASE 0x1000u
#define SPACE     0x2000u

enum {
    REG_TX     = 0x00, /* write a byte here to transmit */
    REG_STATUS = 0x04, /* bit 0: busy */
    REG_ID     = 0x08  /* read-only identity */
};

static uint8_t bus[SPACE];
static unsigned reads;
static unsigned writes;

static volatile uint32_t *reg(uint16_t offset) {
    return (volatile uint32_t *)(void *)(bus + MMIO_BASE + offset);
}

static uint32_t mmio_read(uint16_t offset) {
    reads++;
    /* The ID register is driven by the device, not by memory. Supplying
     * it at read time is what makes this a device rather than an array. */
    if (offset == REG_ID) {
        return 0x5A5A0001u;
    }
    return *reg(offset);
}

static void mmio_write(uint16_t offset, uint32_t value) {
    writes++;
    *reg(offset) = value;
}

int main(void) {
    printf("bus: %u bytes, device window at 0x%04X\n",
           SPACE, MMIO_BASE);
    printf("device id: 0x%08X\n", mmio_read(REG_ID));

    /* Transmit three bytes. The status check is what stops us from
     * overwriting a byte the device has not consumed yet. */
    const char *msg = "Hi!";
    for (size_t i = 0; msg[i] != '\0'; i++) {
        mmio_write(REG_TX, (uint32_t)(unsigned char)msg[i]);
        printf("  sent 0x%02X, status now 0x%08X\n",
               (unsigned)(unsigned char)msg[i], mmio_read(REG_STATUS));
    }

    /* Read the window back through the bus. Alignment matters: these
     * are 32-bit registers at 4-byte boundaries. */
    printf("\nwindow as 32-bit words:\n");
    for (uint16_t off = 0; off < 12; off += 4) {
        uint32_t v = *(volatile uint32_t *)(void *)(bus + MMIO_BASE + off);
        printf("  +0x%02X: 0x%08X\n", off, v);
    }

    printf("\nreads %u, writes %u\n", reads, writes);
    printf("address of REG_TX as an offset: 0x%04X\n", MMIO_BASE + REG_TX);
    printf("bytes in one register: %zu\n", sizeof(uint32_t));
    return 0;
}
```

## Expected output

```text
bus: 8192 bytes, device window at 0x1000
device id: 0x5A5A0001
  sent 0x48, status now 0x00000000
  sent 0x69, status now 0x00000000
  sent 0x21, status now 0x00000000

window as 32-bit words:
  +0x00: 0x00000021
  +0x04: 0x00000000
  +0x08: 0x00000000

reads 4, writes 3
address of REG_TX as an offset: 0x1000
bytes in one register: 4
```

The window read-back shows `0x00000021` at `+0x00`, which is `!` — the
last byte written. Each write overwrote the previous one because the
device never clears a busy bit in this model, so the CPU never waits.
That is the failure mode a real driver avoids: it writes, then spins
until `STATUS` says the byte has been consumed.

The `+0x08` word is `0` even though `mmio_read(REG_ID)` returns
`0x5A5A0001`. Both are correct. `ID` is supplied by the device at read
time, not stored in the array — reading the raw memory underneath it
gives the array's contents, which are zero. A device register is not a
memory location that happens to be special; it is a different thing that
shares the address space.

## Common pitfalls

### Dropping `volatile` because "it works"

Remove the qualifier and the program still prints the same output at
`-O0`. Compile at `-O2` and the ID read may be folded away, or the
status loop hoisted, and the behaviour changes. The bug is latent in the
source, not in the optimisation level — you just cannot see it until the
compiler starts helping.

### Misaligned access

A 32-bit register at an address that is not a multiple of four faults on
many architectures (ARM, and RISC-V without the misaligned-access
extension). On x86 it is merely slow. Place registers at offsets that
respect their size, and let the compiler's `offsetof` checks catch
mistakes in structs.

### Assuming the device window is ordinary memory

`memcpy` into an MMIO region, or `memset` over it, is almost always
wrong: those functions are entitled to use wide vector stores in any
order, and a device may reject a 16-byte write to a 4-byte register, or
interpret it as four separate transactions. Touch device registers one at
a time, through the declared type.

### Port-mapped and memory-mapped confused

If you see `inb(0x60)` in code, that is port-mapped I/O on x86 and it has
nothing to do with addresses in C. The equivalent memory-mapped access
looks like `*(volatile uint8_t *)0x60`. Both exist; they are not
interchangeable, and a driver written for one will not work on the other.
