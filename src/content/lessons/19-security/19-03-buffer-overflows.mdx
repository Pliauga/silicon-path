## The bug that never went away

A buffer overflow is a write past the end of an array. Every C program has them
available by default: array indexing is unchecked, and the language has no
mechanism to change that without ceasing to be C. The first Morris worm used
one in 1988; the vulnerability class is still in the top quarter of reported
CVEs, because the code that contains them is still running.

What makes it a *security* problem rather than a crash is the stack layout. A
function's local variables and its return address live in the same contiguous
region of memory, a few dozen bytes apart. If a write is not bounded, it walks
from the buffer toward the return address. An attacker who controls the bytes
controls where the function returns to, and that is arbitrary code execution.

This lesson teaches the mechanism and never runs it. Every unsafe snippet is
in a fenced block marked as such; the program you compile is the safe version,
and its output is real.

## What you'll be able to do

- Explain what a stack frame holds and why a buffer sits next to a return address.
- Read an unsafe copying pattern and say what an attacker can do with it.
- Replace `strcpy`/`sprintf`/`gets` with bounded equivalents that still compile.
- Say why "it did not crash" is not evidence that a write was in bounds.

## The frame, and why one byte matters

Call a function with a local `char name[8]`. The compiler reserves at least
eight bytes for it, then places the saved registers and the return address
after it. The address of the return is a fixed offset from the start of the
buffer, and it is knowable at runtime — an attacker who can read a stack
address, or who guesses well, knows exactly how many bytes to send.

| Region | What is there | Grows toward |
| --- | --- | --- |
| high addresses | caller's frame | — |
| ... | saved return address | ← written by overflow |
| ... | saved frame pointer | ← written by overflow |
| ... | `char name[8]` | ← the buffer you write into |
| low addresses | red zone, scratch | — |

The diagram explains the whole class. There is no gap between the buffer and
the things that steer the program, and C will not stop you writing into them.

<TheoryBlock label="Why it matters for C" title="The compiler stopped warning, not the bug">

	Modern compilers insert a **stack canary** — a random value between the buffer
	and the return address, checked before the function returns. That converts many
	overflows from code execution into a controlled abort, which is a real
	improvement and not a fix: the write still happened, the data around it is still
	corrupted, and a write far enough past the canary still does damage. `-fstack-protector`
	is a seatbelt. Bounded copies are the brakes.

</TheoryBlock>

## The unsafe pattern, not run

This is the code this lesson exists to warn about. It is written out so you can
recognise it, and it is deliberately not compiled.

```c
/* DO NOT RUN THIS. Kept as an example of the pattern to recognise. */
#include <stdio.h>
#include <string.h>

int main(void) {
    char name[8];
    /* Reads an unbounded number of bytes. There is no size argument,
       because the function has no idea how big the destination is. */
    strcpy(name, "administrator");
    printf("%s\n", name);
    return 0;
}
```

Five things are wrong in seven lines, and only the first is obvious:

1. `strcpy` has no length parameter, so it cannot stop.
2. The source is 13 characters plus a terminator; the destination is 8 bytes.
3. `strcpy`'s signature returns `char *`, so the write is not "checked" anywhere.
4. The compiler emits no diagnostic unless the source is a literal and the
   optimiser happens to see it.
5. The program may print `administrator` and exit zero. The corruption is
   silent, which is why this bug survives review.

The rest of this lesson is the same operation done correctly, compiled, with
its output pasted.

## The same job, bounded

`snprintf` and an explicit capacity solve it. The important detail is that
`snprintf` returns the length it *would* have written, so the return value is
the truncation signal — the buffer contents are not.

```c
#include <stddef.h>
#include <stdio.h>
#include <string.h>

/* The lesson's point in one program: a bounded copy, the truncation signal,
 * and a struct layout you can inspect without ever writing out of bounds.
 *
 * Nothing here overflows. The "what would have been overwritten" half is
 * demonstrated by viewing the struct's own bytes through unsigned char *,
 * which the standard allows for any object. */

enum { NAME_CAP = 8 };

struct account {
    char name[NAME_CAP];
    unsigned balance;
};

/* Bounded copy. `cap` is the size of dst in bytes, including the
 * terminator. Returns 1 when everything fitted, 0 when it was truncated. */
static int copy_name(char *dst, size_t cap, const char *src) {
    size_t need = strlen(src);
    size_t keep = (need < cap - 1) ? need : cap - 1;

    memcpy(dst, src, keep);
    dst[keep] = '\0';
    return need < cap;
}

int main(void) {
    const char *attempts[] = {"ada", "grace", "administrator", ""};
    const size_t count = sizeof attempts / sizeof attempts[0];

    printf("%-16s %-10s %-5s %s\n", "attempt", "stored", "fits", "strlen");
    printf("%-16s %-10s %-5s %s\n", "----------------", "----------",
           "-----", "------");

    struct account acc;
    memset(&acc, 0, sizeof acc);
    acc.balance = 500;

    for (size_t i = 0; i < count; i++) {
        int fits = copy_name(acc.name, sizeof acc.name, attempts[i]);
        printf("%-16s %-10s %-5s %zu\n",
               attempts[i][0] ? attempts[i] : "(empty)",
               acc.name[0] ? acc.name : "(empty)",
               fits ? "yes" : "no",
               strlen(acc.name));
    }

    /* snprintf reports the length it would have written. That return value,
     * not the buffer contents, is the truncation signal. */
    char line[NAME_CAP];
    int would = snprintf(line, sizeof line, "%s", "administrator");
    printf("\nsnprintf wanted %d bytes, the buffer holds %zu\n",
           would, sizeof line);

    /* The layout is why a one-byte overflow is silent: the field sits at
     * offset 0 and the member next to it is padded rather than guarded. */
    printf("\nlayout of struct account:\n");
    printf("  name    offset %zu, %zu bytes\n",
           offsetof(struct account, name), sizeof acc.name);
    printf("  balance offset %zu, %zu bytes\n",
           offsetof(struct account, balance), sizeof acc.balance);
    printf("  struct  %zu bytes total\n", sizeof acc);

    /* Simulate the 9th byte landing on the first byte of balance, legally:
     * view the struct as bytes, which the standard permits for any object. */
    size_t gap = offsetof(struct account, balance) - sizeof acc.name;
    printf("\nspace between name and balance: %zu byte(s)\n", gap);
    printf("so a 9-byte copy into name reaches balance at once\n");

    acc.balance = 500;
    printf("  balance before: %u (0x%08x)\n", acc.balance, acc.balance);

    unsigned char *bytes = (unsigned char *)&acc;
    size_t target = offsetof(struct account, balance);
    printf("  writing 'x' (0x%02x) to byte %zu of the struct\n",
           (unsigned)'x', target);
    bytes[target] = (unsigned char)'x';

    printf("  balance after:  %u (0x%08x)\n", acc.balance, acc.balance);
    printf("  lost 500 - %u = %u from the last byte of the value\n",
           acc.balance, 500u - acc.balance);

    return 0;
}
```

## Expected output

```text
attempt          stored     fits  strlen
---------------- ---------- ----- ------
ada              ada        yes   3
grace            grace      yes   5
administrator    adminis    no    7
(empty)          (empty)    yes   0

snprintf wanted 13 bytes, the buffer holds 8

layout of struct account:
  name    offset 0, 8 bytes
  balance offset 8, 4 bytes
  struct  12 bytes total

space between name and balance: 0 byte(s)
so a 9-byte copy into name reaches balance at once
  balance before: 500 (0x000001f4)
  writing 'x' (0x78) to byte 8 of the struct
  balance after:  376 (0x00000178)
  lost 500 - 376 = 124 from the last byte of the value
```

The table's third row is the whole lesson. `copy_name` was handed 13 bytes and
an 8-byte destination, and it did the only safe thing: it kept seven bytes plus
a terminator and reported `no`. A `strcpy` would have written all 14 and
carried on into `balance`.

The last five lines show why that matters, using a write the standard actually
permits. `balance` begins at offset 8, immediately after the eight-byte name
field, so the ninth byte of a copy lands on `balance`'s least significant byte.
`500` is `0x000001f4`; overwriting the low byte with `0x78` leaves `0x00000178`,
which is 376. Nothing crashed. Nothing printed a warning. A value silently
became a different value — and with a return address instead of a `balance`,
that is code execution.

## Common pitfalls

### Assuming `strncpy` is the safe `strcpy`

It is not. `strncpy(dst, src, n)` stops after `n` bytes and does **not**
terminate when the source is longer than `n`. The result is a buffer holding
non-terminated text, and every later `printf("%s")` reads past its end. It was
designed for fixed-width fields in old Unix structs, not for C strings. Use
`snprintf` or the explicit copy above.

### Trusting `sizeof` on a pointer

`void copy(char *dst) { strncpy(dst, src, sizeof dst); }` copies 8 bytes on a
64-bit machine — the size of the pointer, not the array. `sizeof` on an array
parameter is always the pointer size. Pass the capacity as a second parameter,
as `copy_name` does.

### Measuring safety by whether the program crashed

Most overflows of a few bytes do not crash. They corrupt a neighbouring
variable, or padding, or a saved value that is only read on an error path.
Testing with one short input proves nothing; the bug appears with an input
longer than the buffer, which is the input an attacker will send. Test with the
longest input the field allows, not a typical one.

### Compiling with `-fno-stack-protector` to "make it work"

Disabling a mitigation because a program now aborts is fixing the smoke alarm.
The abort is the canary doing its job and reporting a real write past the end.
Turn the flag back on and fix the copy.
