## Two tools, two different jobs

A cipher hides the content of a message. A hash proves the content has not
changed. They look similar — both turn readable data into unreadable data — and
confusing them is the source of a long list of real vulnerabilities.

A **cipher** is reversible, but only with the key. A **hash** is deliberately
not reversible at all: it takes any amount of input and produces a fixed-size
output, and there is no key. If you encrypt a message and lose the key, the
message is gone. If you hash a message and lose nothing, you still cannot
recover it — that is the point.

Nothing in this lesson is safe to deploy. The constructions are small enough to
read on one screen, which means they are small enough to break. Learning what a
cipher *is* requires seeing one with the walls down; using one requires a
library written by people who do this for a living, and this lesson tells you
which ones.

## What you'll be able to do

## The one reversible operation you can do by hand

XOR has a property nothing else has: it is its own inverse. If `c = p ⊕ k` then
`p = c ⊕ k`. Encrypting and decrypting are the same operation, which makes a
cipher trivial to write and — this is the important part — trivial to get wrong.

The **one-time pad** is the only cipher that is provably unbreakable, and the
proof requires three things that are easy to state and expensive to satisfy:

1. the key is at least as long as the message;
2. the key is truly random;
3. the key is used exactly once, then destroyed.

Drop any one of them and the proof collapses. Real systems drop all three,
because generating and distributing a megabyte of true randomness per megabyte
of traffic is not practical. What they use instead is a **stream cipher**: a
short key expanded into a long keystream by an algorithm. AES in counter mode
and ChaCha20 are the two you will meet. They keep property 1 and 2 as
computational assumptions and absolutely require property 3.

| Property | One-time pad | Stream cipher | What breaks without it |
| --- | --- | --- | --- |
| key ≥ message | required | keystream, generated | reuse reveals overlap |
| truly random | required | pseudo-random | predictable keystream |
| used once | required | **required** | the two plaintexts XOR together |

<TheoryBlock label="Why it matters for C" title="Reuse is a bug your compiler cannot see">

	Two ciphertexts encrypted under the same stream key XOR to the XOR of the two
	plaintexts — the key has cancelled out completely. There is no code path that
	looks wrong, no warning, no crash. An attacker with two ciphertexts recovers the
	difference of the messages and, with a little English text in one of them, both
	messages. This is why nonces exist: a per-message value mixed into the keystream
	so that two encryptions under one key are never the same operation. If you ever
	write encryption code, the nonce is the part to check twice.

</TheoryBlock>

## Seeing the leak

The program below encrypts two twelve-character messages under the same sixteen
bytes of key, then XORs the two ciphertexts together. The key vanishes and what
remains is the XOR of the two plaintexts — computed twice, once from the
ciphertexts and once directly from the messages, to show they are identical.

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

/* A one-time pad, done twice. The first attempt uses a fresh key byte for
   every plaintext byte. The second reuses one key for two messages, which
   is the mistake that has broken every hand-rolled cipher ever shipped. */

#define MAXLEN 24

static void xor_into(const char *plain, const char *key, char *out, size_t n) {
    for (size_t i = 0; i < n; i++) {
        out[i] = (char)(plain[i] ^ key[i]);
    }
    out[n] = '\0';
}

static void print_hex(const char *label, const char *data, size_t n) {
    printf("%-18s", label);
    for (size_t i = 0; i < n; i++) {
        printf("%02x ", (unsigned char)data[i]);
    }
    printf("\n");
}

int main(void) {
    /* Two messages of equal length, plus one key. */
    const char *msg_a = "ATTACKATDAWN";
    const char *msg_b = "DEFENDATNOON";
    const size_t n = strlen(msg_a);

    if (strlen(msg_b) != n) {
        fprintf(stderr, "messages must be the same length for this demo\n");
        return 1;
    }

    /* A real one-time pad needs n truly random bytes, used once, then
       destroyed. These are fixed so the output is reproducible. */
    const unsigned char pad[MAXLEN] = {
        0x5a, 0x1c, 0x93, 0x47, 0x0e, 0xb6, 0x22, 0xd1,
        0x38, 0x6f, 0xa5, 0x04, 0x00, 0x00, 0x00, 0x00,
        0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00
    };

    char ct_a[MAXLEN];
    char ct_b[MAXLEN];

    /* Case 1: separate keys, which is correct. */
    xor_into(msg_a, (const char *)pad, ct_a, n);
    print_hex("plaintext  A:", msg_a, n);
    print_hex("ciphertext A:", ct_a, n);

    /* Case 2: the SAME pad reused for a second message. */
    xor_into(msg_b, (const char *)pad, ct_b, n);

    printf("\nreusing the pad for a second message:\n");
    print_hex("ciphertext B:", ct_b, n);

    /* XOR of the two ciphertexts cancels the key entirely. */
    char leak[MAXLEN];
    for (size_t i = 0; i < n; i++) {
        leak[i] = (char)(ct_a[i] ^ ct_b[i]);
    }
    leak[n] = '\0';
    print_hex("A xor B:", leak, n);

    printf("\nsame as the plaintexts xored, key gone: ");
    for (size_t i = 0; i < n; i++) {
        unsigned char c = (unsigned char)(msg_a[i] ^ msg_b[i]);
        printf("%02x ", c);
    }
    printf("\n");

    /* Where both messages share a letter the difference is zero. */
    size_t matches = 0;
    for (size_t i = 0; i < n; i++) {
        if (msg_a[i] == msg_b[i]) {
            matches++;
        }
    }
    printf("%zu of %zu positions are identical in the two plaintexts\n", matches, n);
    printf("every one of them shows up as 00 in the xor above\n");

    return 0;
}
```

## Expected output

```text
plaintext  A:     41 54 54 41 43 4b 41 54 44 41 57 4e 
ciphertext A:     1b 48 c7 06 4d fd 63 85 7c 2e f2 4a 

reusing the pad for a second message:
ciphertext B:     1e 59 d5 02 40 f2 63 85 76 20 ea 4a 
A xor B:          05 11 12 04 0d 0f 00 00 0a 0e 18 00 

same as the plaintexts xored, key gone: 05 11 12 04 0d 0f 00 00 0a 0e 18 00 
3 of 12 positions are identical in the two plaintexts
every one of them shows up as 00 in the xor above
```

Look at the zeros. Positions 7, 8, and 12 (counting from 1) are `00` because
both messages have a `T` at 7 and 8 and an `N` at 12 — `ATTACKATDAWN` and
`DEFENDATNOON` agree in three places, and every agreement shows through as a
zero byte. That is already a structural leak: the attacker now knows where the
messages match without knowing what they say.

Recovering the rest is a short exercise in guessing. `05` is the XOR of `A` and
`D`. Try crib-dragging: assume one message contains a common word, XOR it
against the difference, and see whether the result looks like English.

## Hashes: one way, fixed size

A hash maps any input to a fixed-size output, and it must be hard to find two
inputs with the same output. That second property — **collision resistance** —
is what makes a hash useful for integrity, and it is the property that older
functions like MD5 and SHA-1 have lost.

| Function | Output | Status today |
| --- | --- | --- |
| MD5 | 128 bits | broken; collisions are cheap to produce |
| SHA-1 | 160 bits | broken; collisions demonstrated in 2017 |
| SHA-256 | 256 bits | fine for integrity |
| BLAKE3 | 256 bits | fine, and faster than SHA-256 |

A hash is not encryption and a hash is not a password store on its own. For
passwords you want a deliberately slow hash — Argon2, scrypt, bcrypt — because
the threat model is offline guessing at scale, and speed is the attacker's
advantage. For file integrity or message authentication you want a fast one.

## Common pitfalls

### Writing your own cipher

Every property of a real cipher — diffusion, resistance to differential
cryptanalysis, constant-time comparison — is invisible in the source and
measurable only with years of analysis. The correct move in C is to link a
library: libsodium's `crypto_secretbox` or OpenSSL's EVP interface. A
hand-rolled XOR loop is a teaching aid and a vulnerability, in that order.

### Comparing secrets with `==` or `strcmp`

Both stop at the first differing byte, so the time they take reveals how much
of the guess was correct. At 10⁹ guesses per second, the microseconds saved per
guess are enough to recover a value byte by byte. Use a constant-time
comparison such as `CRYPTO_memcmp` or `sodium_memcmp`.

### Seeding a "random" key from `rand()`

`rand()` is deterministic from its seed, and the seed is usually the time. Two
processes started in the same second produce the same key. Keys come from the
operating system's CSPRNG — `/dev/urandom`, `getrandom()` on Linux,
`SecRandomCopyBytes` on macOS — and never from `rand()` or `srand(time(NULL))`.

### Believing a hash proves authorship

A checksum in the same place as the file protects against corruption, not
against tampering: whoever can replace the file can replace its checksum. Only
a signature with a key the attacker does not hold proves authorship.
