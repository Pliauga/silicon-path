## One region per request

The simplest way to manage memory is to hand out one contiguous run of
bytes per request and remember exactly where it starts and how long it
is. No tables, no indirection: a pointer and a length. Every allocator
from `malloc` down to the kernel's physical frame allocator starts here.

The bookkeeping is a list of blocks sorted by address. Each block is
either **free** or **in use**, and its neighbours are known by their
position in the list rather than by stored pointers. To satisfy a
request, find a free block big enough, split it into the part you hand
out and the remainder, and mark the front half used. To release, mark a
block free and merge it with any free neighbours, because two adjacent
free blocks are the same resource as one large one.

That merge step is where most of the interesting behaviour comes from.
Without it, a program that allocates and frees repeatedly ends up with a
heap peppered with useless one-byte gaps even though more than enough
total memory exists. With it, the only holes left are the ones genuinely
pinned between live blocks.

## What you'll be able to do

- Explain the difference between internal and external fragmentation.
- Trace first fit, best fit, and worst fit over the same request script.
- Say why best fit can leave the heap in a worse shape than first fit.
- Coalesce adjacent free blocks and describe what happens if you do not.

## Two kinds of waste

The vocabulary is worth getting straight, because the two forms have
opposite fixes.

| | Internal fragmentation | External fragmentation |
| --- | --- | --- |
| Where the waste is | Inside an allocated block | In the free list |
| Cause | The allocator rounds up to a fixed unit | Many small holes, each too small to use |
| Who notices | The program that asked for 5 and got 16 | The program that asks for 16 and is refused |
| Fix | Smaller unit, or a size class per request | Compaction, or a different allocation scheme |

A contiguous allocator with exact-size splits has no internal
fragmentation: ask for 12 bytes and the block is 12 bytes. Paging, in
the next lesson, trades that away — it rounds every request up to 4096 —
in exchange for eliminating the external kind. Neither is free, and no
scheme removes both.

External fragmentation is the interesting one because it is
*statistical*. You cannot predict from a sequence of requests whether the
heap will fragment, only measure it. That is why the three placement
policies below are worth comparing on a fixed script rather than
reasoning about in the abstract.

First fit takes the first hole that is big enough. Best fit takes the
smallest hole that works, on the theory that it wastes the least space.
Worst fit takes the largest hole, on the theory that the leftover will
still be big enough to be useful. Only one of these theories survives
contact with a real workload, and the program below shows which.

<TheoryBlock label="Why it matters for C" title="Your heap is exactly this list">

	`malloc` maintains a free list with exactly this structure, plus
	headers. glibc's allocator rounds requests into size classes, splits
	and coalesces chunks, and keeps bins for common sizes — but the
	underlying question is still "which free chunk do I take". The
	practical consequence: a program that allocates many small blocks,
	frees some of them in a scattered order, then asks for one large block
	can fail with plenty of memory free. That failure is external
	fragmentation, and no amount of `malloc` tuning removes it.

## Three policies, one script

The program keeps a 64-byte heap as a block list. It allocates five
blocks, frees two of them to punch holes of different sizes, then asks
for an 8-byte block and a 16-byte one. All three policies run the same
script, so any difference in the result is the policy's doing.

```c
#include <stdio.h>
#include <string.h>

/* Three placement policies over the same 64-byte heap.
 *
 * A contiguous allocator keeps one list of blocks in address order, each
 * either free or in use, and answers one question per request: which
 * free block do I split? The three classic answers differ only in how
 * they rank the candidates. Splitting and coalescing are identical, so
 * any divergence below is the policy's doing. */

#define HEAP      64
#define MAX_BLOCKS 16

struct block {
    int start;
    int size;
    int used;
};

struct heap {
    struct block blocks[MAX_BLOCKS];
    int count;
};

enum strategy { FIRST, BEST, WORST };

static void heap_reset(struct heap *h)
{
    h->count = 1;
    h->blocks[0] = (struct block){0, HEAP, 0};
}

static int free_holes(const struct heap *h, int *largest)
{
    int holes = 0;
    *largest = 0;

    for (int i = 0; i < h->count; i++) {
        if (!h->blocks[i].used) {
            holes++;
            if (h->blocks[i].size > *largest) {
                *largest = h->blocks[i].size;
            }
        }
    }
    return holes;
}

static int pick(const struct heap *h, int size, enum strategy strategy)
{
    int choice = -1;

    for (int i = 0; i < h->count; i++) {
        const struct block *b = &h->blocks[i];
        if (b->used || b->size < size) {
            continue;
        }
        if (strategy == FIRST) {
            return i;                    /* lowest address */
        }
        if (choice == -1) {
            choice = i;
        } else if (strategy == BEST && b->size < h->blocks[choice].size) {
            choice = i;                  /* smallest hole that fits */
        } else if (strategy == WORST && b->size > h->blocks[choice].size) {
            choice = i;                  /* largest hole */
        }
    }
    return choice;
}

/* Allocate `size` bytes and return the block index in use, or -1. */
static int allocate(struct heap *h, int size, enum strategy strategy)
{
    int slot = pick(h, size, strategy);
    if (slot == -1) {
        return -1;
    }

    struct block *b = &h->blocks[slot];
    int leftover = b->size - size;

    if (leftover > 0) {
        /* Shift everything above the slot up to make room for the tail. */
        for (int k = h->count; k > slot + 1; k--) {
            h->blocks[k] = h->blocks[k - 1];
        }
        h->count += 1;
        h->blocks[slot + 1] = (struct block){b->start + size, leftover, 0};
    }
    h->blocks[slot].size = size;
    h->blocks[slot].used = 1;
    return slot;
}

/* Mark a block free, then merge it with any adjacent free neighbours.
 * Without this step the heap becomes a confetti of one-byte holes; with
 * it, the only holes left are the ones pinned between live blocks --
 * which is external fragmentation, and the reason a 16-byte request can
 * fail on a heap with 16 bytes free. */
static void release(struct heap *h, int slot)
{
    if (slot < 0 || slot >= h->count) {
        return;
    }
    h->blocks[slot].used = 0;

    for (int i = 0; i + 1 < h->count; ) {
        if (!h->blocks[i].used && !h->blocks[i + 1].used) {
            h->blocks[i].size += h->blocks[i + 1].size;
            for (int k = i + 1; k < h->count - 1; k++) {
                h->blocks[k] = h->blocks[k + 1];
            }
            h->count -= 1;
        } else {
            i++;
        }
    }
}

/* An ASCII map of the heap, sixteen bytes per character column. */
static void draw(const struct heap *h)
{
    char row[HEAP + 1];
    char ruler[HEAP + 1];

    memset(row, ' ', sizeof row);
    row[HEAP] = '\0';
    for (int i = 0; i < h->count; i++) {
        char mark = h->blocks[i].used ? '#' : '.';
        for (int k = 0; k < h->blocks[i].size; k++) {
            row[h->blocks[i].start + k] = mark;
        }
    }

    for (int i = 0; i < HEAP; i++) {
        ruler[i] = (i % 8 == 0) ? '|' : '-';
    }
    ruler[HEAP] = '\0';

    printf("  %s\n  %s\n", ruler, row);
}

int main(void)
{
    /* The script: fill most of the heap, then punch two holes with
     * different sizes, then ask for an 8-byte block and a 16-byte one.
     * The hole sizes are 12 and 8, so the 8-byte request is the first
     * point at which the three policies can disagree. */
    const int sizes[] = {12, 20, 8, 12, 8};
    const int n = (int)(sizeof sizes / sizeof sizes[0]);
    const char *names[] = {"first fit", "best fit", "worst fit"};

    for (int s = FIRST; s <= WORST; s++) {
        struct heap h;
        int handles[5];

        heap_reset(&h);
        for (int i = 0; i < n; i++) {
            handles[i] = allocate(&h, sizes[i], (enum strategy)s);
        }

        /* Free the first and third allocations: a 12-byte hole low in the
         * heap and an 8-byte hole in the middle, separated by live data. */
        release(&h, handles[0]);
        release(&h, handles[2]);

        int filled = allocate(&h, 8, (enum strategy)s);
        int big = allocate(&h, 16, (enum strategy)s);

        int largest = 0;
        int holes = free_holes(&h, &largest);

        printf("%s\n", names[s]);
        draw(&h);
        printf("  holes %d, largest %d bytes, 8-byte request %s, "
               "16-byte request %s\n\n",
               holes, largest,
               filled == -1 ? "refused" : "placed",
               big == -1 ? "refused" : "placed");
    }

    printf("each row is the same heap after the same operations.\n");
    return 0;
}
```

## Expected output

```text
first fit
  |-------|-------|-------|-------|-------|-------|-------|-------
  ########....####################........####################....
  holes 3, largest 8 bytes, 8-byte request placed, 16-byte request refused

best fit
  |-------|-------|-------|-------|-------|-------|-------|-------
  ............################################################....
  holes 2, largest 12 bytes, 8-byte request placed, 16-byte request refused

worst fit
  |-------|-------|-------|-------|-------|-------|-------|-------
  ########....####################........####################....
  holes 3, largest 8 bytes, 8-byte request placed, 16-byte request refused

each row is the same heap after the same operations.
```

Read the map left to right: `#` is in use, `.` is free, and the `|`
marks every eighth byte. The first and third rows are identical, which
is not a bug — see below.

**First fit** took the first hole big enough, which was the 12-byte one
low in the heap, leaving a 4-byte remainder. The 8-byte hole in the
middle stayed untouched until the 16-byte request, which failed because
the largest hole is 8.

**Best fit** picked the 8-byte hole for the 8-byte request, leaving no
remainder at all, and the 12-byte hole survived intact. This is the only
row where a 16-byte request would still fail — 12 is not 16 — but it is
the row with the *fewest* holes and the *largest* remaining hole. Best
fit used the smallest sufficient block correctly, and the heap is in the
best shape of the three.

**Worst fit** is identical to first fit here, and the reason is
instructive: at the moment the 8-byte request arrives, the two holes are
12 and 8, and the largest is 12 — the same block first fit took. Worst
fit and first fit coincide whenever the first hole that fits is also the
largest. That happens often on a heap whose low addresses were filled
first, which is exactly what a growth-by-allocation program produces.

The honest summary is that this script does not separate first fit from
worst fit, and it barely separates either from best fit. Real allocator
benchmarks run millions of requests drawn from a distribution, because a
handful of requests is not enough data to rank the policies. What this
program *does* show is the mechanism, and the fact that the difference
between the policies is three lines of comparison.

The 16-byte refusal in all three rows is the point of the whole lesson.
Count the free bytes at the end of the first row: 4 at address 8, 8 at
address 32, and 4 at address 60. That is 16 bytes free — exactly what the
next request asks for — and the request is refused, because no single
run is longer than 8. The bottom row is the same total split into
12 + 4. Fragmentation is not a shortage of memory; it is a shortage of
*consecutive* memory.

## Common pitfalls

### Splitting a block but forgetting to grow the list

When a free block is split, the block list gets one entry longer. If the
new entry is written past the end of the array — or if `count` is not
incremented — the allocator appears to work until the heap reaches
`MAX_BLOCKS`, at which point it either corrupts memory or silently loses
the remainder. Every allocator has a maximum number of blocks for exactly
this reason.

### Coalescing only with the next block

Two-pass bugs are common: the release loop merges `i` with `i+1`, then
moves on, so a chain of three free blocks becomes two. The loop in the
program above deliberately does not advance on a merge, so a run of any
length collapses in one call. Test it by freeing four adjacent blocks and
checking the hole count is one, not three.

### Assuming best fit always wins

Best fit leaves the smallest remainders, which sounds optimal and often
is, but it also leaves many tiny fragments that are useless to any later
request. First fit tends to leave one large hole at the end of the heap,
which is more useful in practice — and it is faster, because it stops
scanning at the first hit. The measurement in the output above happens to
favour best fit on hole count; a different script would not.

### Trusting an address to stay valid after compaction

Compaction is impossible for a general-purpose allocator because the
program holds raw pointers to the blocks. Moving a block invalidates
every pointer to it, and C has no mechanism to update them — this is
precisely the problem paging solves by moving the *mapping* instead of
the data.

### Reporting fragmentation as a percentage of free memory

"40% fragmented" is meaningless without saying which request sizes fail.
The only useful statement is "an N-byte request cannot be satisfied by a
hole of size M", which is a fact about the largest hole, not about the
total.
