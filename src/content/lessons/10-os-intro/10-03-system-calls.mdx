## The one gate into the kernel

Userland cannot execute privileged instructions, but it does need files, memory,
and other processes. The **system call** is the sanctioned crossing point: a
userland program puts arguments in registers, executes a trap instruction, and
the CPU switches to kernel mode at a fixed address. The kernel does the work,
puts a result in a register, and returns.

Everything you think of as "the OS" from inside a C program is one of these
calls or a library function wrapping one. `open`, `read`, `write`, `close`,
`fork`, `execve`, `wait4`, `mmap`, `brk` — all of them.

## What you'll be able to do

- Define a system call and name the trap that crosses the boundary.
- Explain why `printf` is not a system call and `write` is.
- Read a raw return value and `errno` together instead of trusting the printed text.
- Turn a failing descriptor into a message with `perror`.

<TheoryBlock label="Why it matters for C" title="printf is not a system call">

	`printf` formats a string in user memory and appends it to a `FILE *` buffer. It crosses into the
	kernel only when that buffer fills or you call `fflush`. This is why redirecting output to a file
	can reorder lines that looked ordered on a terminal: a terminal flushes per line, a file does not.
</TheoryBlock>

## The cost is real

A system call is not a function call. The trap itself is cheap on modern CPUs,
but the transition flushes parts of the pipeline, may touch a different address
space, and defeats branch prediction. The order of magnitude is hundreds of
nanoseconds to a few microseconds, against a few nanoseconds for an in-process
call.

That gap is why `stdio` exists at all. A program that called `write` once per
character would be correct and roughly a thousand times slower than one that
buffers a line. The buffer is not an optimization detail; it is the layer that
amortizes the crossing.

## Calling `write` directly, and failing on purpose

The next program uses the raw call, then deliberately calls it with a descriptor
the process does not own, so you can see the error path.

```c
#define _POSIX_C_SOURCE 200809L

#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void) {
    const char *greeting = "hello from a system call\n";

    /* write() is the system call itself. It returns a byte count. */
    ssize_t written = write(STDOUT_FILENO, greeting, strlen(greeting));
    if (written < 0) {
        perror("write");
        return 1;
    }
    printf("write() returned  %zd\n", written);
    printf("strlen() returned %zu\n", strlen(greeting));

    /* Ask the kernel to write to a descriptor this process does not own. */
    errno = 0;
    ssize_t bad = write(99, "x", 1);
    if (bad < 0) {
        printf("\nwrite() to fd 99 failed\n");
        printf("errno  = %d\n", errno);
        printf("reason = %s\n", strerror(errno));
    }

    /* printf() is a library function, not a system call. It returns the
       number of characters it buffered, or a negative value on failure. */
    int printed = printf("\nthis line went through printf()\n");
    printf("printf() returned %d\n", printed);
    return 0;
}
```

`ssize_t` is a signed size type, because a system call reports failure as `-1`
and a plain `size_t` cannot hold that. `%zd` matches `ssize_t`; `%zu` matches
`size_t`.

`<unistd.h>`, `write`, and the `STDOUT_FILENO` constant are POSIX, not ISO C.
Windows has a `_write` in `<io.h>` with a different signature, and no
`STDOUT_FILENO`; portable code uses `<stdio.h>` and lives with the buffer.

## Expected output

```text
hello from a system call
write() returned  25
strlen() returned 25

write() to fd 99 failed
errno  = 9
reason = Bad file descriptor

this line went through printf()
printf() returned 33
```

Three things are worth pausing on.

`write` and `strlen` agree on 25 because `write` was given exactly the string
length, and it wrote all of it. A short write is legal — `write` may return fewer
bytes than requested — which is why serious code loops until the count is
satisfied.

`errno` is 9, `EBADF`, because descriptor 99 was never opened. Compare against
`EBADF`, not against 9.

`printf` returned 33: the length of `"this line went through printf()\n"`. It is
reporting characters *buffered*, not characters the kernel has accepted yet.

## Common pitfalls

### Checking only `exit(0)` and not the return value

`printf` returns a negative value if the write eventually fails — a full disk, a
closed pipe. Ignoring it is the difference between a program that detects a
broken output and one that reports success while dropping data. This matters in
module 18 when output goes to a file.

### Mixing `write` and `printf` and expecting order

They use different buffers. `printf` writes into the stdio buffer; `write` goes
straight to the kernel. Interleave them and the order can differ from the source.
Call `fflush(stdout)` before a raw `write` if the order matters — this lesson's
program does not need to, because the raw write comes first, but the moment you
reverse them you will see it.

### Assuming a short read means end of file

`read` returning 0 means end of file. Returning less than you asked for means
"that is all that was available right now". A pipe with a writer still attached
can do this indefinitely. Treat `0` as the terminator and loop on nonzero.
