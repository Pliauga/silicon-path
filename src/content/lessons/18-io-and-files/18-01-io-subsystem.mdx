## The part of the machine that waits

Every other lesson in this course has measured time in nanoseconds. A register
read is a fraction of a cycle. A cache hit is about four cycles. Main memory is
a couple of hundred. Then the I/O subsystem arrives and the numbers stop being
comparable: a fast NVMe drive takes about 100 microseconds to answer, a spinning
disk takes about 10 milliseconds, and a network round trip across an ocean takes
about 150 ms.

A CPU running at 3 GHz retires roughly 300 instructions in the time an NVMe
read takes. It retires roughly 30 million in the time a disk seek takes. That
gap is why the operating system goes to so much trouble around I/O, and why the
shape of your C program — how many I/O operations it issues, not how much data
it moves — usually decides whether it is fast.

Two words carry most of this lesson. A **block device** is one that reads and
writes fixed-size chunks, usually 4 KiB, and cannot address a single byte. A
**character device** is one that streams bytes, like a keyboard or a serial
port. File systems are built on block devices, and the block size is the reason
you will see writes padded to 4096 bytes.

## What you'll be able to do

- Convert a device's quoted throughput into the time one 4 KiB block takes.
- Explain why latency, not bandwidth, decides the cost of many small writes.
- Describe what the buffer cache is doing between your `write()` and the disk.
- Say which of buffered, unbuffered, and memory-mapped I/O suits which job.

## Bandwidth is not latency

Marketing quotes throughput in MB/s. That number answers exactly one question:
how long does a large, sequential transfer take. It says nothing about the first
byte, which is what your program spends its life waiting for.

The arithmetic is simple enough to do on paper. A device that moves `R`
megabytes per second moves `R × 10⁶` bytes per second, so one block of `B` bytes
takes `B × 10⁶ / (R × 10⁶)` seconds — which is `B / R` microseconds. For 4096
bytes at 3500 MB/s that is about 1.17 µs. Small enough that the transfer time
disappears into the controller's own latency.

| Device | Quoted rate | One 4 KiB block | Ticks on a 3 GHz core |
| --- | --- | --- | --- |
| Hard disk | 150 MB/s | 27.3 µs | 81,918 |
| SATA SSD | 550 MB/s | 7.4 µs | 22,341 |
| NVMe SSD | 3500 MB/s | 1.17 µs | 3,510 |
| Gigabit Ethernet | 125 MB/s | 32.8 µs | 98,304 |

Notice the ordering that surprises people: gigabit Ethernet, which sounds fast,
moves a block more slowly than a 2010-era hard disk. The wire is not the
bottleneck; the protocol and the software stack are.

<TheoryBlock label="Why it matters for C" title="One write call is not one disk write">

	`fwrite` copies your bytes into a `FILE` buffer in user memory and returns
	immediately. The kernel sees nothing until that buffer fills or you call `fflush`.
	Below that, the kernel's own page cache holds the data until a writeback thread
	decides to push it to the device — typically a few seconds later. So a loop writing
	4000 small records may issue four actual device writes, and `fflush` controls only
	the first of those two buffers. That is why a program can look fast and still lose
	data when the machine dies.

</TheoryBlock>

## Four ways to talk to a device

The interfaces stack, and each layer trades control for convenience.

| Interface | Call | Buffered by | Good for | Cost of a call |
| --- | --- | --- | --- | --- |
| stdio | `fwrite`, `fprintf` | your `FILE` + kernel | text, formatted output | ~100 ns |
| POSIX | `write`, `read` | kernel only | binary data, exact control | ~1 µs |
| Direct | `O_DIRECT`, `fsync` | neither | databases, journaling | milliseconds |
| Memory-mapped | `mmap` | kernel pages | random access to a large file | page faults |

Each step down that table gives you more control and costs more per operation.
The mistake beginners make is jumping to the bottom for no reason: `write()` in
a loop is slower than `fwrite()` in a loop, because you have thrown away a
buffer and paid a system call for every handful of bytes.

The opposite mistake is just as common. A program that writes a log line and
then dies without `fflush` or `fclose` has handed the line to a buffer that will
never be drained. There is nothing to recover, because the bytes were never
anywhere else.

## Seeing the gap in numbers

Timing a real disk from inside a program is unreliable: the file may already be
cached, the drive may be busy, and a laptop's power management moves the number
by more than the effect you are measuring. What is perfectly deterministic is
the arithmetic that the subsystem forces on you.

```c
#include <stdio.h>
#include <stdint.h>

/* One 4 KiB block, moved over four devices with very different rates.

   A device quoted in MB/s moves `mb` million bytes every second, so one
   block of `bytes` takes bytes * 1e9 / (mb * 1e6) nanoseconds, which is
   bytes * 1000 / mb. Integer arithmetic keeps every digit exact. */

struct device {
    const char *name;
    uint32_t mb_per_second;
};

int main(void) {
    const uint64_t block_bytes = 4096;

    const struct device devices[] = {
        {"hard disk   150 MB/s",  150},
        {"SATA SSD    550 MB/s",  550},
        {"NVMe SSD   3500 MB/s", 3500},
        {"ethernet   125 MB/s",  125}
    };
    const size_t count = sizeof devices / sizeof devices[0];

    printf("%llu bytes in one block, %zu devices\n\n",
           (unsigned long long)block_bytes, count);

    for (size_t i = 0; i < count; i++) {
        uint64_t ns = block_bytes * 1000 / devices[i].mb_per_second;
        printf("%-22s %6llu ns  %3llu.%03llu us\n",
               devices[i].name,
               (unsigned long long)ns,
               (unsigned long long)(ns / 1000),
               (unsigned long long)(ns % 1000));
    }

    printf("\nblock time in ticks of a 3 GHz core:\n");
    for (size_t i = 0; i < count; i++) {
        uint64_t ns = block_bytes * 1000 / devices[i].mb_per_second;
        printf("%-22s %6llu ticks\n",
               devices[i].name,
               (unsigned long long)(ns * 3));
    }

    return 0;
}
```


The right-hand column is the one worth staring at. A single block from a hard
disk is 82,000 cycles of nothing but waiting. If your program issues that read
and then blocks, the CPU is idle for 27 microseconds — long enough to context
switch to another process and back twice. This is the entire motivation for
asynchronous I/O and for the kernel's readahead: do something else, or ask for
the next block before you need it.

## Common pitfalls

### Assuming `fwrite` reached the disk

`fwrite` returns the number of elements it accepted into the `FILE` buffer.
That is a statement about your process's memory, not about the device. Even
`fflush` only pushes data to the kernel. Only `fsync(fileno(f))` — POSIX, not
ISO C — asks the kernel to wait for the device. A program that writes a
receipt and exits normally is fine because `exit` flushes; a program that
`_exit`s or crashes loses everything still buffered.

### Measuring I/O speed with a stopwatch

The second run of a file read is often a hundred times faster than the first,
because the page cache is holding the data. Benchmarks that skip a cache flush
measure memory bandwidth and report it as disk speed. If you must measure,
repeat the run and report the minimum and the median, never a single number.

### Forgetting that `fopen` can fail

`fopen` returns `NULL` for a missing directory, a permission problem, or an
exhausted descriptor table. Dereferencing it is undefined behaviour and on
most systems an immediate crash. Every `fopen` in this module is followed by a
check, and every check closes what it opened on the error path.

### Treating a partial write as an error

`fwrite` can legally write fewer elements than you asked for when the
destination is a pipe or a full disk. The correct response is to check the
return value and either retry or report, not to assume the buffer is gone. The
same is true of `read`/`write`, which return a byte count for exactly this
reason.
