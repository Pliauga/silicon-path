## Nine bits and a rule about who is asking

Every protection system answers the same question: may *this* subject perform
*that* operation on *this* object? The Unix answer fits in nine bits stored in
the inode. Three classes of user — owner, group, other — each get three
permissions: read (4), write (2), execute (1).

The classes are checked in order and the first match wins. If you are the
owner, the owner bits decide, full stop; the group bits are never consulted,
even when they would have granted more. That ordering is the single most
misunderstood part of the model, and it is the reason a file with mode `0600`
cannot be read by anyone but its owner no matter what group they are in.

| Mode | Owner | Group | Other | Typical use |
| --- | --- | --- | --- | --- |
| `0600` | `rw-` | `---` | `---` | private key, personal note |
| `0644` | `rw-` | `r--` | `r--` | ordinary document |
| `0664` | `rw-` | `rw-` | `r--` | shared document |
| `0755` | `rwx` | `r-x` | `r-x` | directory, program |
| `0777` | `rwx` | `rwx` | `rwx` | almost always a mistake |

The leading zero matters in C. `600` is a decimal literal; `0600` is octal and
equals 384 decimal. Writing `chmod(path, 600)` by accident grants permissions
that look nothing like what you intended, and it compiles without complaint.

## What you'll be able to do

- Read a mode as three octal digits and say what each class may do.
- Check a permission bit in C by shifting and masking.
- Explain why a directory needs execute permission to be entered.
- Say what happens when a process's user is both owner and group member.

## Directories are not files

The three permission bits mean different things depending on what they are
attached to, and this trips up almost everyone once.

| Bit | On a file | On a directory |
| --- | --- | --- |
| `r` | read the contents | list the names in it |
| `w` | modify the contents | create, delete, or rename entries |
| `x` | execute it | traverse it — look up a name inside |

A directory with `r` but not `x` lets you list the names and nothing else. A
directory with `x` but not `r` lets you open a file whose name you already know,
but hides the listing. And deleting a file requires write permission on the
*directory*, not on the file — which is why you can delete a read-only file in a
directory you own, and why you cannot delete a file in a directory you do not.

<TheoryBlock label="Why it matters for C" title="The kernel checks, not your program">

	When a program calls `open("/etc/shadow", O_RDONLY)`, the check happens inside
	the kernel against the real user ID of the process. There is no way to talk your
	way past it from user space, and no C code you can write changes the answer. That
	is the point of a protection system: the enforcement is in a layer your program
	cannot modify. A **setuid** binary is the one exception — it runs with the file
	owner's ID instead of yours — and every setuid bug ever found is a bug in that
	exception.

</TheoryBlock>

## Denying by default

A protection system that decides *what to allow* grows a list of exceptions. A
system that decides *what to deny* and then permits explicitly stays auditable:
everything is forbidden unless a rule says otherwise. The Unix model is the
second kind — no bits set means no access — and so is every firewall default.

## Checking the bits in C

The program below implements the permission check the way the kernel does it —
shift to the right class, mask the three bits, and ask whether the requested
permission is present. It also computes a mode string and clears a single bit
with a mask.

```c
#include <stdio.h>

/* Permission bits as a plain integer: 3 bits each for owner, group, other.
   The same low nine bits a real inode stores. */

#define R_BIT 4u
#define W_BIT 2u
#define X_BIT 1u

struct rule {
    const char *name;
    unsigned mode;   /* only the low 9 bits matter */
};

static int allowed(unsigned mode, int who, unsigned need) {
    /* who: 0 owner, 1 group, 2 other. Shift 3 bits per class. */
    unsigned shift = 3u * (unsigned)(2 - who);
    unsigned bits = (mode >> shift) & 7u;
    return (bits & need) == need;
}

static void describe(const struct rule *r) {
    printf("%-10s 0%03o  ", r->name, r->mode);

    static const char *who[] = {"owner", "group", "other"};
    for (int i = 0; i < 3; i++) {
        unsigned shift = 3u * (unsigned)(2 - i);
        unsigned bits = (r->mode >> shift) & 7u;
        printf("%s=%c%c%c ", who[i],
               (bits & R_BIT) ? 'r' : '-',
               (bits & W_BIT) ? 'w' : '-',
               (bits & X_BIT) ? 'x' : '-');
    }
    printf("\n");
}

int main(void) {
    const struct rule rules[] = {
        {"private",  0600u},
        {"script",   0755u},
        {"shared",   0664u},
        {"readonly", 0444u},
        {"public",   0777u}
    };
    const size_t count = sizeof rules / sizeof rules[0];

    for (size_t i = 0; i < count; i++) {
        describe(&rules[i]);
    }

    printf("\ncan a stranger read each one?\n");
    for (size_t i = 0; i < count; i++) {
        printf("%-10s %s\n", rules[i].name,
               allowed(rules[i].mode, 2, R_BIT) ? "yes" : "no");
    }

    printf("\ncan the owner run each one?\n");
    for (size_t i = 0; i < count; i++) {
        printf("%-10s %s\n", rules[i].name,
               allowed(rules[i].mode, 0, X_BIT) ? "yes" : "no");
    }

    printf("\nremoving the group write bit from 0664:\n");
    unsigned shared = 0664u;
    unsigned shift = 3u;           /* group class sits above the low 3 bits */
    shared &= ~(W_BIT << shift);
    printf("0664 -> 0%03o\n", shared);

    return 0;
}
```

```text

script     0755  owner=rwx group=r-x other=r-x 
shared     0664  owner=rw- group=rw- other=r-- 
readonly   0444  owner=r-- group=r-- other=r-- 
public     0777  owner=rwx group=rwx other=rwx 

can a stranger read each one?
private    no
script     yes
shared     yes
readonly   yes
public     yes

can the owner run each one?
private    no
script     yes
shared     no
readonly   no
public     yes

removing the group write bit from 0664:
0664 -> 0644
```

The last three lines are the interesting ones. `private` is readable by nobody
but its owner, and the group and other columns stay empty no matter how many
people share the owner's group. And `~` is what makes a bit-clearing mask: the
complement of `0o020` inside a 32-bit `unsigned` is a word with every bit set
except that one.

One thing this program does not model: the kernel checks the owner class
*first and only*. A real `access()` call would refuse the owner of `0600` even
if they were also in a group granted read. The `allowed` function above is
per-class, so it can answer "what would the group rule say"; the kernel asks a
different question.

## Common pitfalls

### Writing `chmod(path, 644)` instead of `0644`

Without the leading zero, `644` is decimal and equals octal `1204`, which sets
bits outside the permission field entirely. The call usually fails with
`EINVAL` and occasionally does something surprising. Every mode literal in C
starts with `0`, and the compiler will not warn you.

### Expecting group permissions to add to owner permissions

They do not stack. A process whose user is the file's owner is judged by the
owner bits alone, so adding a group grant cannot give the owner more access.
The corollary: when a program starts failing after a mode change, check which
class it is being evaluated as before changing the bits again.

### Believing `x` on a script is enough

The `x` bit lets the kernel try to execute the file. For a shell script the
kernel reads the `#!` line and runs the named interpreter, which then needs
read permission on the script — and the interpreter must be readable by the
same user. For a compiled binary only `x` is needed, because the kernel maps
it directly.

### Setting `0777` to "make it work"

A world-writable file or directory in a shared location is a privilege
escalation waiting to happen: anyone can replace the contents with something
the owner will later execute. The correct fix is to give the specific group
the specific bits, or to run the service as its own user.
