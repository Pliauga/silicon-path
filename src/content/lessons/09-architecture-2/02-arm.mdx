## A RISC design that took over the small machines

ARM started in 1985 as a processor for a British computer that never sold
well. It now runs in essentially every phone, most tablets, and an
increasing number of laptops and servers. The reason is not that it was
the fastest design — it was that it was the most *efficient* one, and
efficiency mattered enormously once computers started running on
batteries.

The architecture has changed a lot since 1985: 32-bit, then 64-bit, then
thumb encodings, then vector extensions. What survived is a small set of
decisions made early.

## Fixed width is the gift to the decoder

Every ARM instruction in the classic 32-bit encoding is exactly four
bytes. The processor always knows where the next instruction begins: at
the current address plus four. It can fetch several at once and decode
them in parallel.

Variable-width instructions cannot do this. The decoder has to read the
first bytes, work out the length, and only then find the next
instruction — a serial process that caps how many can start per cycle.

| Encoding | Width       | Finding the next instruction |
| -------- | ----------- | ---------------------------- |
| ARM      | 4 bytes     | always `pc + 4`              |
| Thumb    | 2 or 4 bytes | read the first halfword first |
| x86      | 1–15 bytes  | decode to discover the length |

## Fields of a data-processing instruction

A classic ARM data-processing instruction puts an opcode, two register
numbers, and a 12-bit immediate into one 32-bit word.

| Bits    | Field  | Meaning                        |
| ------- | ------ | ------------------------------ |
| 27–24   | opcode | which operation                |
| 19–16   | Rn     | first source register          |
| 15–12   | Rd     | destination register           |
| 11–0    | imm12  | immediate value                |

Four bits per register field is not an accident. It is the reason ARM has
sixteen registers: r0 through r15, where r13 is the stack pointer, r14 is
the link register, and r15 is the program counter.

<TheoryBlock label="Why it matters for C" title="Register count is why ARM has no x86-style register pressure">

	C compilers allocate variables to registers, and the number available
	sets how much of a function can stay in them. x86-64 has sixteen
	general-purpose registers; ARM64 has thirty-one. That difference is
	visible in generated code: a complex function on x86 spills to the stack
	earlier and reloads more often. If you have ever wondered why the same
	C compiles to noticeably different code on a Mac with Apple silicon, this
	is part of the answer.
</TheoryBlock>

## Decoding words by hand

The program below decodes three real ARM instruction words, extracting
each field with shifts and masks. This is precisely what a disassembler
does, minus the tables.

```c
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

/* Decode fixed-width 32-bit instruction words the way an ARM core must:
 * every instruction is four bytes, so the decoder never has to guess a
 * length. The field layout here is the data-processing form, simplified. */

enum {
    OP_SHIFT = 21, OP_MASK = 0x0fu,
    RN_SHIFT = 16, RD_SHIFT = 12, IMM12_MASK = 0x0fffu
};

static const char *op_name(unsigned op) {
    switch (op) {
    case 0x0: return "AND";
    case 0x2: return "SUB";
    case 0x4: return "ADD";
    default:  return "other";
    }
}

int main(void) {
    const uint32_t words[] = {
        0xE2811001u, /* ADD r1, r1, #1    */
        0xE2412004u, /* SUB r2, r1, #4    */
        0xE20130FFu, /* AND r3, r1, #0xFF */
    };

    printf("%-11s %-6s %-4s %-4s %s\n", "word", "opcode", "Rn", "Rd", "imm12");
    for (size_t i = 0; i < sizeof words / sizeof words[0]; i++) {
        uint32_t w = words[i];
        unsigned op  = (w >> OP_SHIFT) & OP_MASK;
        unsigned rn  = (w >> RN_SHIFT) & 0x0fu;
        unsigned rd  = (w >> RD_SHIFT) & 0x0fu;
        unsigned imm = w & IMM12_MASK;

        printf("0x%08X  %-6s r%-3u r%-3u 0x%03X\n", w, op_name(op), rn, rd, imm);
    }

    /* A four-bit register field is why the encoding stops at r15. */
    printf("registers addressable by one field: %u\n", 1u << 4);
    printf("instruction width in bytes: %zu\n", sizeof words[0]);
    return 0;
}
```

## Expected output

```text
word        opcode Rn   Rd   imm12
0xE2811001  ADD    r1   r1   0x001
0xE2412004  SUB    r1   r2   0x004
0xE20130FF  AND    r1   r3   0x0FF
registers addressable by one field: 16
instruction width in bytes: 4
```

Check the first row by hand. `0xE2811001` shifted right by 21 and masked
with `0x0f` gives 4, which the table maps to ADD. Bits 19–16 give 1, so
`Rn` is r1. Bits 15–12 give 1, so `Rd` is also r1. The low twelve bits
give 1, so the immediate is 1. The instruction is `ADD r1, r1, #1`, and
the disassembly comment says exactly that.

Nothing in that decoding needed to know how long the instruction was. It
was four bytes because every ARM instruction is four bytes.

## Common pitfalls

### Forgetting that the immediate is limited

Twelve bits holds values up to 4095, and even that is optimistic — the
real ARM encoding rotates an 8-bit value, so many twelve-bit patterns are
not encodable. Loading `0x12345678` takes more than one instruction. This
is a genuine cost of fixed-width encoding and the reason ARM has a
separate literal-pool mechanism.

### Assuming ARM and ARM64 are the same instruction set

They are not. AArch64 has thirty-one general-purpose registers, fixed
32-bit instructions with a different field layout, and no conditional
execution on most instructions. Code written for 32-bit ARM will not run
on a 64-bit core without recompiling, and in some cases will not run at
all.

### Thinking the program counter is a general register

In 32-bit ARM, r15 is the program counter and can be read and written
like any other register. That is convenient and dangerous: a misaligned
write to r15 jumps somewhere arbitrary. In AArch64 the PC is no longer
directly addressable, partly for this reason.
