## Faster clocks stopped working

For forty years, each generation of processor was faster because its
clock was faster. Around 2005 that stopped: pushing the clock higher
raised power consumption faster than performance, and the chips melted.
The industry's answer was to put several cores on one die and run them at
a reasonable speed.

That worked, with a catch. Two cores do twice the work only if the work
can be split. A program that computes one long dependency chain gets no
benefit at all — the second core has nothing to do.

## What you'll be able to do

- State Amdahl's law and use it to bound a speedup.
- Explain why the serial fraction sets the ceiling.
- Compute when adding cores stops being worth it.
- Say why multicore made concurrency a C programmer's problem.

## The ceiling is the serial part

If a fraction *p* of the work can run in parallel, the best possible
speedup on *n* cores is:

```text
speedup(n) = 1 / ((1 - p) + p / n)
```

As *n* grows, the `p/n` term shrinks to nothing and the denominator
approaches `1 - p`. So the ceiling is `1 / (1 - p)`, no matter how many
cores you add.

| Parallel fraction | 2 cores | 4 cores | 8 cores | 16 cores | Ceiling |
| ----------------- | ------- | ------- | ------- | -------- | ------- |
| 50%               | 1.33×   | 1.61×   | 1.78×   | 1.88×    | 2.0×    |
| 90%               | 1.81×   | 3.12×   | 4.76×   | 6.66×    | 10×     |
| 99%               | 2.00×   | 4.00×   | 7.69×   | 14.28×   | 100×    |

A program that is 90% parallel gets a 10× ceiling. Sixteen cores buy it
6.66×, and the remaining 3.34× is unreachable — not because the hardware
is bad, but because 10% of the work refuses to be divided.

<TheoryBlock label="Why it matters for C" title="This is why threads became unavoidable">

	Before multicore, concurrency in C was for servers and operating
	systems. After multicore, a single-threaded program uses a quarter of the
	machine it runs on. That is the pressure that made pthreads, atomics, and
	memory models part of ordinary C work — and it is why modules 11 through
	15 exist. The hardware change forced the language change.
</TheoryBlock>

## Computing the table

Integer arithmetic keeps the output exact and identical on every machine,
which matters more here than decimal precision: the point is the shape of
the curve, not the third digit.

```c
#include <stdio.h>

/* Amdahl's law: if a fraction p of the work can run in parallel, the best
 * speedup on n cores is 1 / ((1 - p) + p / n). Integer maths so the output
 * is exact and reproducible everywhere. */

static void print_row(unsigned parallel_percent, unsigned max_cores) {
    printf("parallel fraction %u%%\n", parallel_percent);
    for (unsigned n = 1; n <= max_cores; n *= 2) {
        /* serial + parallel/n, scaled by 100 for integer arithmetic. */
        unsigned long denom = (100u - parallel_percent) + parallel_percent / n;
        unsigned long speedup_x100 = (100u * 100u) / denom;
        printf("  %2u cores  speedup %lu.%02lux\n",
               n, speedup_x100 / 100, speedup_x100 % 100);
    }
    printf("\n");
}

int main(void) {
    print_row(50, 16);
    print_row(90, 16);
    print_row(99, 16);
    return 0;
}
```

## Expected output

```text
parallel fraction 50%
   1 cores  speedup 1.00x
   2 cores  speedup 1.33x
   4 cores  speedup 1.61x
   8 cores  speedup 1.78x
  16 cores  speedup 1.88x

parallel fraction 90%
   1 cores  speedup 1.00x
   2 cores  speedup 1.81x
   4 cores  speedup 3.12x
   8 cores  speedup 4.76x
  16 cores  speedup 6.66x

parallel fraction 99%
   1 cores  speedup 1.00x
   2 cores  speedup 2.00x
   4 cores  speedup 4.00x
   8 cores  speedup 7.69x
  16 cores  speedup 14.28x

```

The 50% row is the sobering one. Sixteen cores deliver 1.88× — almost
all of the possible 2×, and almost none of the possible 16×. Going from
eight cores to sixteen adds one tenth of a times speedup. That is what a
serial half of the program does to a machine with sixteen cores.

The 99% row shows the opposite: doubling the cores nearly doubles the
throughput, right up to sixteen. Between 90% and 99% parallel lies most
of the difference between a program that scales and one that does not.

Note the integer arithmetic: `p / n` truncates, so at `p = 99` and `n = 4`
the parallel term is 24, not 24.75. The printed values are therefore
slightly pessimistic. That is acceptable for a table whose point is the
asymptote, and it is honest — the program does not claim a precision it
does not have.

## Common pitfalls

### Expecting linear speedup

Four cores does not mean four times faster. It means at most four times
faster, and usually much less. Anyone quoting a 4× speedup on a quad-core
machine is either measuring a perfectly parallel workload or mismeasuring.

### Forgetting the overhead of coordination

Amdahl's law assumes dividing work is free. It is not: threads cost
memory, cache coherence traffic, and locking. Beyond some core count,
adding another thread makes the program slower. The law is an upper
bound, and real speedups sit below it.

### Confusing cores with threads

Two threads on one core interleave; they do not run simultaneously. This
is why oversubscribing a machine with threads gives no speedup for
CPU-bound work, and why a program that is fast on eight threads may be
identical on eight cores' worth of four threads.

### Assuming the serial fraction is fixed

It is not — it depends on the input size. The serial setup cost is often
constant while the parallel work grows with the data, so a program that is
50% serial on a small input becomes 99% parallel on a large one. This is
the **weak scaling** argument, and it is why "does it scale?" is a
question about your workload rather than about the hardware.
