## Choosing a victim

Step 3 of the fault sequence says "if no frame is free, choose a victim".
That single sentence hides the entire subject of this lesson, because the
choice is made with incomplete information. The kernel knows what has been
accessed; it does not know what will be accessed next. Every replacement
policy is a guess about the future dressed up as a bookkeeping rule about
the past.

The guessing is not hopeless. Programs exhibit **locality of reference**:
they touch a small set of pages now and a related small set a moment
later. That property is what makes any policy work at all, and it is why
the two classical policies below get within a few percent of each other
on real workloads while differing wildly on adversarial ones.

Two policies, one difference:

- **FIFO** evicts the page that arrived earliest. A page's timestamp is
  set when it is loaded and never updated.
- **LRU** evicts the page that was used least recently. The timestamp is
  refreshed on every hit.

The intuition for LRU is the locality assumption taken literally: the
page you used longest ago is the one least likely to be needed next.
FIFO has no such story — it evicts the oldest arrival even if that page
is being hammered right now.

## What you'll be able to do

- Trace FIFO and LRU by hand on a reference string.
- Explain why FIFO can evict a page that is in constant use.
- State Belady's anomaly and construct a small example.
- Say which page-table bit makes LRU approximate rather than exact.

## The comparison, in one table

| Property            | FIFO                              | LRU                                |
| ------------------- | --------------------------------- | ---------------------------------- |
| Victim rule         | earliest load                     | least recent use                   |
| Updated on a hit    | no                                | yes                                |
| Bookkeeping         | a queue, O(1) per access          | needs ordering, O(1) with a list   |
| Prone to            | evicting a hot page               | evicting a page needed far ahead   |
| Anomaly             | Belady's — more frames, more faults | none: LRU is a stack algorithm   |

The last row is the one worth unpacking. A policy is a **stack
algorithm** if the set of pages resident with *n* frames is always a
subset of the set resident with *n+1* frames. LRU has this property —
adding a frame can only add a page to the resident set, never remove one
— and stack algorithms can never suffer Belady's anomaly. FIFO is not a
stack algorithm, and the counter-example is the famous reference string
`1 2 3 4 1 2 5 1 2 3 4 5`: with three frames FIFO takes 9 faults and with
four frames it takes 10.

<TheoryBlock label="Why it matters for C" title="Your access pattern is the policy">

	Since exact LRU needs a timestamp per access — which no hardware
	maintains — real kernels approximate it with the **accessed** bit in
	the page table entry. The MMU sets the bit in hardware on every
	access, and the kernel periodically clears all of them and later reads
	back which ones were set. Pages never marked were not used since the
	last sweep, and become candidates. This is why the policy in a real
	kernel is closer to "clock" than to LRU, and why a C program that
	walks a large array in a hostile order can beat the policy no matter
	what the policy is.

</TheoryBlock>

## Two policies, one line apart

The program traces both policies over two reference strings with three
frames each. The policies share every line of code except where the
recency timestamp is updated: FIFO leaves it at load time, LRU refreshes
it on a hit.

```c
#include <stdio.h>

/* FIFO and LRU over the same reference string.
 *
 * Both policies maintain a set of resident pages and both have a fault
 * when the page is not in it. They differ in one line of bookkeeping:
 * FIFO evicts by    when a page arrived, LRU by when it was last used.
 * That single difference is enough to make them disagree on the same
 * input, and the disagreement is not a tie -- one of them is strictly
 * better here, and neither is always better in general. */

#define FRAMES 3

struct memory {
    int frame[FRAMES];
    int since[FRAMES];   /* FIFO: insert tick. LRU: last-use tick. */
    int tick;
    int faults;
};

static void reset(struct memory *m)
{
    for (int i = 0; i < FRAMES; i++) {
        m->frame[i] = -1;
        m->since[i] = 0;
    }
    m->tick = 0;
    m->faults = 0;
}

/* Returns the frame index holding `page`, or -1. */
static int find(const struct memory *m, int page)
{
    for (int i = 0; i < FRAMES; i++) {
        if (m->frame[i] == page) {
            return i;
        }
    }
    return -1;
}

/* The oldest entry in `since`, which is the eviction victim for both
 * policies. FIFO's `since` is never refreshed on a hit; LRU's is. */
static int victim(const struct memory *m)
{
    int oldest = 0;
    for (int i = 1; i < FRAMES; i++) {
        if (m->since[i] < m->since[oldest]) {
            oldest = i;
        }
    }
    return oldest;
}

static int access_page(struct memory *m, int page, int use_lru, int verbose)
{
    int slot = find(m, page);
    int fault = 0;

    m->tick++;

    if (slot != -1) {
        if (use_lru) {
            m->since[slot] = m->tick;
        }
        if (verbose) {
            printf("  %2d  hit   page %d in frame %d\n", page, page, slot);
        }
        return 0;
    }

    fault = 1;
    m->faults++;

    /* Prefer an empty frame before evicting anything. */
    slot = -1;
    for (int i = 0; i < FRAMES; i++) {
        if (m->frame[i] == -1) {
            slot = i;
            break;
        }
    }
    if (slot == -1) {
        slot = victim(m);
    }

    if (verbose) {
        printf("  %2d  FAULT page %d into frame %d (evicted %d)\n",
               page, page, slot, m->frame[slot] == -1 ? -1 : m->frame[slot]);
    }

    m->frame[slot] = page;
    m->since[slot] = m->tick;
    return fault;
}

static int run(const int *reference, int n, int use_lru, int verbose)
{
    struct memory m;
    reset(&m);

    if (verbose) {
        printf("%s\n", use_lru ? "LRU" : "FIFO");
    }
    for (int i = 0; i < n; i++) {
        access_page(&m, reference[i], use_lru, verbose);
    }
    if (verbose) {
        printf("  faults: %d of %d references\n\n", m.faults, n);
    }
    return m.faults;
}

int main(void)
{
    /* The classic string that separates the two policies. With three
     * frames it produces 9 faults under FIFO and 10 under LRU: more
     * history is not automatically better history. */
    const int a[] = {1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5};
    const int na = (int)(sizeof a / sizeof a[0]);

    printf("reference string:");
    for (int i = 0; i < na; i++) {
        printf(" %d", a[i]);
    }
    printf("\n%d frames\n\n", FRAMES);

    int fifo = run(a, na, 0, 1);
    int lru = run(a, na, 1, 1);

    printf("summary for the first string: FIFO %d faults, LRU %d faults\n\n",
           fifo, lru);

    /* A second string with strong locality. Now LRU wins, because the
     * page it keeps is the page that will be asked for next. */
    const int b[] = {1, 2, 3, 1, 4, 5, 1, 2, 3, 4};
    const int nb = (int)(sizeof b / sizeof b[0]);

    printf("reference string:");
    for (int i = 0; i < nb; i++) {
        printf(" %d", b[i]);
    }
    printf("\n%d frames\n\n", FRAMES);

    fifo = run(b, nb, 0, 1);
    lru = run(b, nb, 1, 1);
    printf("summary for the second string: FIFO %d faults, LRU %d faults\n",
           fifo, lru);
    return 0;
}
```

The first string is the honest bad news: **LRU does worse than FIFO**,
10 faults against 9. Follow the two traces at reference 7 — the `5` —
and the reason is visible. Both policies have `1 2` resident and have to
choose. FIFO evicts `4`, because `4` arrived at position 4 and is the
oldest. LRU also evicts `4`, because `4` was last used at position 4 and
nothing has been used since; the same choice, from opposite reasoning.

They diverge at reference 10, the `3`. FIFO evicts `1` — the oldest
arrival — and `1` is about to be needed again at reference 11. LRU evicts
`5`, which is the page used least recently, and then misses on `4` and
`5` instead. Over twelve references the policies are within one fault of
each other and FIFO happens to win. The lesson is not that FIFO is good;
it is that a policy can lose on one string and win on another, and that
LRU's guarantee is about *frame count*, not about beating FIFO on any
particular input.

The second string has strong locality — `1`, `2`, `3` then `1` again,
then a run of `1 2 3 4` — and now LRU wins 8 to 9. Look at reference 7:
LRU has `1` still resident because it was used at position 4, and hits.
FIFO had evicted `1` at position 5 to make room for `4`, and misses.
That is the whole argument for the recency heuristic, in one line of
trace.

Neither result generalises. What generalises is the shape: FIFO's
weakness is evicting on arrival order with no regard to use, and it shows
up whenever the oldest page is also the hottest.

## Common pitfalls

### Believing LRU is always better than FIFO

It is not, and this program shows a twelve-reference string where FIFO
wins by one fault. LRU's guarantee is that it never suffers Belady's
anomaly, which is a statement about what happens when you *add a frame*,
not about any fixed comparison with another policy.

### Conflating LRU with optimal

The optimal policy, Belady's MIN, evicts the page whose next use is
furthest in the future. It is unimplementable — it needs the future — and
it exists to bound how much better a real policy could possibly be. LRU
is a heuristic that approximates it under locality; on a cyclic access
pattern larger than memory, LRU is pessimal and MIN is not.

### Forgetting that real kernels approximate

Exact LRU requires a timestamp update on every memory access, which would
mean a write to memory on every instruction. Hardware does not do it.
Kernels use the accessed bit, swept periodically, and evict pages that
were not touched in the last interval. The algorithm is called clock or
second-chance, and its fault counts differ from textbook LRU in exactly
the cases where the sweep interval is comparable to the reuse distance.

### Assuming a fault always costs a write

An evicted page costs a write only if its dirty bit is set. Read-only
code pages are clean and can be dropped, and the frame reused
immediately. A workload of pure computation over a read-only text
segment can churn frames with almost no disk traffic; a workload of
writes to a large heap pays for every eviction. This asymmetry is why
"swap usage" alone does not tell you whether a machine is in trouble.

### Measuring with too short a reference string

Three frames and twelve references is a teaching example, not a
benchmark. Policies that differ by one fault in twelve can differ by
orders of magnitude on a workload that is just above the frame count, and
by nothing at all on one that fits. Vary both the frame count and the
string length before drawing a conclusion.
