## An instruction is a number

Your C source becomes a sequence of bytes. Each instruction is a small
number — the **opcode** — optionally followed by the data it operates on.
`0x01` might mean "load this immediate value"; `0x03` might mean "store
the accumulator into memory". The CPU has no idea what any of it means in
human terms. It reads the opcode, jumps to a table of behaviours wired
into silicon, and does the thing.

The **program counter** is the only thing that makes a sequence of numbers
into a program. It holds the address of the next instruction, and after
each instruction it advances — by one, or by some larger amount, or
somewhere else entirely if the instruction was a jump. That is the whole
control flow of every program ever written.

## What you'll be able to do

- Describe fetch–decode–execute in one sentence and name what changes each cycle.
- Read a two-byte instruction and say what its opcode and operand mean.
- Explain why a program stored in memory is what makes `if` possible.
- Say what a jump does to the program counter, and what it does not do.

## Fetch, decode, execute

The cycle is three steps and it never changes.

| Step    | What happens | What holds the result |
| ------- | ------------ | --------------------- |
| Fetch   | memory is read at the address in the program counter | the instruction register |
| Decode  | the opcode is looked up in the control unit's table | the control signals |
| Execute | the operation runs; the counter advances or jumps | registers, memory, or the counter |

Two facts follow, and both matter more than the vocabulary.

First, instructions and data are the same kind of object: bytes in memory.
Nothing in the hardware distinguishes them. A program that computes an
address and jumps to it — a return from a function, a virtual call — is
doing exactly what the fetch step does every cycle.

Second, the program counter is a register like any other. A jump is just
a write to it. There is nothing special about control flow at the
hardware level; `if` is a conditional write to the counter.

## A machine small enough to read

The interpreter below defines eight opcodes and runs a nine-instruction
program on them. It prints the program as bytes first, so the encoding is
visible, then traces every fetch. Nothing here is a model of a real
instruction set — real ones have addressing modes, flags, and variable
length encoding — but every idea in this lesson is present in it.

```c
#include <stdint.h>
#include <stdio.h>

/* Eight opcodes is enough to make the point: an instruction is a small
 * number, and a program is an array of those numbers. */

enum opcode {
    OP_HALT  = 0,
    OP_LOADI = 1, /* accumulator = immediate operand   */
    OP_LOADM = 2, /* accumulator = memory[operand]     */
    OP_STORE = 3, /* memory[operand] = accumulator     */
    OP_DEC   = 4, /* accumulator -= 1                  */
    OP_JNZ   = 5, /* pc = operand if accumulator != 0  */
    OP_PRINT = 6  /* print the accumulator             */
};

struct instruction {
    uint8_t op;
    int8_t operand;
};

/* The program is data. That is the von Neumann idea stated exactly. */
static const struct instruction program[] = {
    {OP_LOADI, 3},   /* 0: acc = 3               */
    {OP_STORE, 0},   /* 1: mem[0] = 3            */
    {OP_LOADM, 0},   /* 2: acc = mem[0]  <- loop */
    {OP_PRINT, 0},   /* 3: show it               */
    {OP_DEC,   0},   /* 4: acc -= 1              */
    {OP_STORE, 0},   /* 5: mem[0] = acc          */
    {OP_JNZ,   2},   /* 6: back to 2 if nonzero  */
    {OP_PRINT, 0},   /* 7: the zero              */
    {OP_HALT,  0}    /* 8: stop                  */
};

static const char *name_of(uint8_t op) {
    switch (op) {
    case OP_LOADI: return "LOADI";
    case OP_LOADM: return "LOADM";
    case OP_STORE: return "STORE";
    case OP_DEC:   return "DEC";
    case OP_JNZ:   return "JNZ";
    case OP_PRINT: return "PRINT";
    case OP_HALT:  return "HALT";
    default:       return "????";
    }
}

int main(void) {
    const size_t count = sizeof program / sizeof program[0];

    /* The program as bytes. Each instruction is two bytes: an opcode and
     * an operand. Two bytes per instruction is a design decision, not a
     * law of nature; real machines use one to six. */
    printf("the program as bytes:\n");
    for (size_t i = 0; i < count; i++) {
        printf("  %2zu: %02X %02X\n", i, program[i].op,
               (unsigned)(uint8_t)program[i].operand);
    }
    printf("  %zu bytes for %zu instructions\n\n",
           count * sizeof(struct instruction), count);

    printf("pc  op     arg   acc before\n");
    printf("--  -----  ---   ----------\n");

    int memory[4] = {0, 0, 0, 0};
    int accumulator = 0;
    size_t pc = 0;
    int steps = 0;

    while (steps < 64) {
        /* FETCH: the program counter says which cell to read. */
        struct instruction ir = program[pc];
        printf("%2zu  %-5s  %3d   %d\n", pc, name_of(ir.op), ir.operand,
               accumulator);
        steps++;

        /* DECODE and EXECUTE. One case per opcode, nothing clever. */
        switch (ir.op) {
        case OP_LOADI:
            accumulator = ir.operand;
            pc++;
            break;
        case OP_LOADM:
            accumulator = memory[(unsigned)ir.operand & 3u];
            pc++;
            break;
        case OP_STORE:
            memory[(unsigned)ir.operand & 3u] = accumulator;
            pc++;
            break;
        case OP_DEC:
            accumulator--;
            pc++;
            break;
        case OP_JNZ:
            pc = (accumulator != 0) ? (size_t)ir.operand : pc + 1;
            break;
        case OP_PRINT:
            printf("            -> %d\n", accumulator);
            pc++;
            break;
        case OP_HALT:
            printf("            halted after %d instructions\n", steps);
            return 0;
        default:
            printf("            unknown opcode 0x%X\n", ir.op);
            return 1;
        }
    }
    printf("            ran past %d instructions without halting\n", steps);
    return 1;
}
```

```text
            -> 1

            -> 0

```

Read the byte dump first. Instruction 0 is `01 03`: opcode `LOADI`, operand
3. Instruction 6 is `05 02`: opcode `JNZ`, operand 2 — a jump back to
instruction 2, which only an encoding like this makes visible as a single
number. The whole program is 18 bytes, and a machine that could only hold
those 18 bytes could run it.

Then read the trace. The program counter does not advance blindly: at
`pc 6` it reads `JNZ 2` and the next line is `pc 2`, not `pc 7`. It makes
that jump three times, once for each pass where the accumulator is
nonzero, and falls through on the fourth when the accumulator reaches
zero.

The accumulator ends at 0, and the loop exits. That exit is the
conditional write to the program counter failing. There is no separate
"loop" mechanism.

## Why this makes `if` possible

A jump that is taken or not taken depending on a value is all a branch
needs. Real machines add flags: a compare sets a zero flag, and `JZ` reads
that flag instead of testing the accumulator. The mechanism is the same —
the program counter is written, or it is not.

That is also why a mispredicted branch is expensive. The CPU guesses which
way the branch goes and starts fetching ahead. Guess wrong, and everything
fetched past the branch has to be discarded.

## Common pitfalls

### Thinking instructions are a different kind of memory

On a von Neumann machine they are the same bytes in the same memory. This
is why a buffer overflow that overwrites a return address works: the
attacker writes bytes that the program counter will later treat as code.
Segments and page permissions exist to make that harder, not because the
hardware distinguishes instructions from data.

### Assuming instruction width is fixed

x86 instructions are one to fifteen bytes; ARM64 is fixed at four. A
variable width means the decoder cannot know where the next instruction
starts without decoding the current one, which is a real cost in the fetch
stage.

### Reading an opcode dump as if byte order were free

`05 02` on a little-endian machine is the two-byte value `0x0205` if you
read it as a `uint16_t`, not `0x0502`. Instruction encoding usually
defines its own field order inside the bytes and does not follow the
machine's endianness, which is exactly why disassembling is a job for a
tool rather than for hand arithmetic.

### Confusing the program counter with a stack pointer

The counter says where the *next instruction* is. The stack pointer says
where *local data* is. A function call writes the return address to the
stack and then jumps — both registers move, which makes them easy to
conflate in a trace.
