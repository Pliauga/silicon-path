## The four calls that are enough

POSIX threads — **pthreads** — has a large API. Four calls cover almost every
program in this course:

| Call | Purpose | Returns 0 on success |
| --- | --- | --- |
| `pthread_create(&t, NULL, fn, arg)` | start a thread running `fn(arg)` | yes |
| `pthread_join(t, &ret)` | wait for it, collect its return value | yes |
| `pthread_mutex_lock(&m)` | enter a critical section | yes |
| `pthread_mutex_unlock(&m)` | leave it | yes |

The signatures encode two important decisions. The thread function is
`void *(*)(void *)`: one pointer in, one pointer out. And the calls return an
error code instead of setting `errno` — you check `!= 0` directly.

`pthread_t` is an opaque handle. It is not a PID, and printing it with `%d` is
undefined because its type varies by platform.

## What you'll be able to do

- Write the four pthread calls a basic program needs, and check each return code.
- Pass data into a thread through the `void *` argument without corrupting it.
- Join every thread so the total does not depend on the schedule.
- Explain why `pthread_t` must not be printed with `%d`.

<TheoryBlock label="Why it matters for C" title="The void pointer is how you pass anything">

	The `void *` argument is the only channel into the thread. For an `int` you cast through
	`intptr_t`; for a struct you pass its address and make sure it outlives the thread. That cast is
	where beginners lose values, because `(void *)` of a small int and a pointer are different things
	on some platforms and the compiler will not always tell you.
</TheoryBlock>

## Four threads, one deterministic total

```c
#define _POSIX_C_SOURCE 200809L

#include <pthread.h>
#include <stdio.h>

#define THREADS 4
#define PER_THREAD 1000

static long partial[THREADS];

static void *sum_slice(void *arg) {
    long index = (long)arg;
    long total = 0;

    for (long i = 0; i < PER_THREAD; i++) {
        total += index * PER_THREAD + i;
    }
    partial[index] = total;     /* each thread owns its own slot */
    return NULL;
}

int main(void) {
    pthread_t threads[THREADS];

    for (long i = 0; i < THREADS; i++) {
        if (pthread_create(&threads[i], NULL, sum_slice, (void *)i) != 0) {
            fprintf(stderr, "could not create thread %ld\n", i);
            return 1;
        }
    }
    for (int i = 0; i < THREADS; i++) {
        if (pthread_join(threads[i], NULL) != 0) {
            fprintf(stderr, "could not join thread %d\n", i);
            return 1;
        }
    }

    long total = 0;
    for (int i = 0; i < THREADS; i++) {
        total += partial[i];
    }

    /* Deterministic: 0 + 1 + ... + 3999 */
    printf("sum of 0..%d = %ld\n", THREADS * PER_THREAD - 1, total);
    return 0;
}
```

This program is deliberately free of races. Each thread writes `partial[index]`
for a distinct `index`, so no two threads touch the same slot. The main thread
reads them only after every join has returned, which is a memory barrier: the
writes are guaranteed visible.

Every program in this lesson needs the thread library linked, so the compile
command carries one extra flag:

```text
gcc -std=c11 -Wall -Wextra -pthread threads.c -o threads
```

Without `-pthread` the link fails with undefined references to
`pthread_create` and `pthread_join`. The flag does two things: it links the
library and it defines the feature-test macros that make the header declare the
full API.

That is the pattern for any parallel reduction — partition the output, join, then
combine on one thread.

## Expected output

```text
sum of 0..3999 = 7998000
```

That value is fixed by arithmetic, not by timing: the four partial sums are
added in index order after all threads finish. However the scheduler interleaves
the threads, the answer is the same. This is the property to look for when you
review thread code — can you name a reason the result is independent of ordering?

Strictly, `(void *)i` where `i` is a `long` is a pointer-sized integer cast. It
works on every platform this course targets because `long` and a pointer are the
same size on LP64. On Windows, `long` is 32 bits and the cast would truncate —
`intptr_t` from `<stdint.h>` is the portable spelling.

## Common pitfalls

### Casting the argument back to `int` instead of `long`

```c
long index = (int)arg;      /* wrong on a platform where long is 64-bit */
```

The value fits here, but the cast says the author did not think about sizes. Use
`intptr_t` or, in this program, `(long)arg` consistently on both sides.

### Joining a thread whose id was overwritten

`pthread_t` values are only valid until joined. Reusing a `pthread_t` variable
across `pthread_create` calls before joining leaks the previous thread's handle.
One array slot per thread, as above, avoids it.

### Not checking the return of `pthread_create`

The call fails with `EAGAIN` at the thread limit. Proceeding without checking
means you later join an uninitialised `pthread_t`, which is undefined behaviour
and often a crash.

### Returning a pointer to thread-local storage

`return &some_local;` from the thread function hands back an address in a stack
frame that no longer exists. The joiner reads garbage. Small values go through
the `void *` return directly; larger results go into a struct the caller
allocated.
