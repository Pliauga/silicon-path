## Three ways to use more than one thread

Pthreads gives you the primitives; it does not tell you how to arrange them. Four
arrangements cover almost everything real software does:

| Model | Shape | Cost | Seen in |
| --- | --- | --- | --- |
| thread per task | one thread per request, exit when done | high with many tasks | simple servers |
| worker pool | fixed N threads drain a queue | bounded, predictable | most servers, web app compilers |
| pipeline | stages connected by queues | good for streaming | video, shell pipelines |
| fork–join | split, work, combine | simple to reason about | numeric code |

The worker pool is the default for a reason: it bounds the number of threads
regardless of how many tasks arrive, so memory and scheduling stay predictable.
A thread per task under load creates thousands of threads and spends more time
switching than working.

## What you'll be able to do

- Compare thread-per-task, worker pool, pipeline, and fork–join on cost and shape.
- Explain why a fixed pool bounds memory when a thread-per-task server does not.
- Claim a task atomically so two workers never run the same one.
- Keep order-dependent output on one thread so the result stays deterministic.

<TheoryBlock label="Why it matters for C" title="The queue is shared, so the claim must be atomic">

	The pool's only shared state is "which task is next". Everything else — the task's own data, its
	result slot — belongs to one worker at a time. Getting the claim right is a two-instruction
	critical section: read the counter, increment it, release the lock. Get it wrong and two workers
	run the same task, which is module 14's race condition with a friendlier face.
</TheoryBlock>

## A fixed pool draining a fixed queue

```c
#define _POSIX_C_SOURCE 200809L

#include <pthread.h>
#include <stdio.h>

#define WORKERS 4
#define TASKS 8

/* A tiny fixed queue of independent tasks. This is the worker-pool model:
   a small number of threads drain a larger number of jobs. */

static int task_value[TASKS] = { 3, 1, 4, 1, 5, 9, 2, 6 };
static int next_task = 0;
static long result[TASKS];
static pthread_mutex_t queue_lock = PTHREAD_MUTEX_INITIALIZER;

static void *worker(void *arg) {
    (void)arg;

    for (;;) {
        pthread_mutex_lock(&queue_lock);
        int slot = next_task;
        if (slot < TASKS) {
            next_task++;        /* claim the job while holding the lock */
        }
        pthread_mutex_unlock(&queue_lock);

        if (slot >= TASKS) {
            return NULL;        /* queue drained */
        }

        result[slot] = (long)task_value[slot] * task_value[slot];
    }
}

int main(void) {
    pthread_t pool[WORKERS];

    for (int i = 0; i < WORKERS; i++) {
        if (pthread_create(&pool[i], NULL, worker, NULL) != 0) {
            fprintf(stderr, "could not create worker %d\n", i);
            return 1;
        }
    }
    for (int i = 0; i < WORKERS; i++) {
        if (pthread_join(pool[i], NULL) != 0) {
            fprintf(stderr, "could not join worker %d\n", i);
            return 1;
        }
    }

    /* Results land in slot order no matter which worker ran which task. */
    long total = 0;
    for (int i = 0; i < TASKS; i++) {
        printf("task %d: %d squared is %ld\n", i, task_value[i], result[i]);
        total += result[i];
    }
    printf("total of all squares = %ld\n", total);
    return 0;
}
```

`pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;` is the static initialiser,
correct for a mutex with file scope. `pthread_mutex_init` is for one inside a
struct or allocated at runtime.

Compile with `-pthread`:

```text
gcc -std=c11 -Wall -Wextra -pthread pool.c -o pool
```

## Expected output

```text
task 0: 3 squared is 9
task 1: 1 squared is 1
task 2: 4 squared is 16
task 3: 1 squared is 1
task 4: 5 squared is 25
task 5: 9 squared is 81
task 6: 2 squared is 4
task 7: 6 squared is 36
total of all squares = 173
```

No "possible orderings" caveat here, and that is deliberate. The workers finish
in an unpredictable order, but every line is printed by the **main** thread after
every join, iterating `i` from 0. The output is a function of the task array, not
of the schedule.

The rule this generalizes to: keep the order-dependent part on one thread, and
let the parallel part write into disjoint slots.

## Common pitfalls

### Claiming the task outside the lock

```c
int slot = next_task;          /* no lock */
pthread_mutex_lock(&queue_lock);
next_task++;
pthread_mutex_unlock(&queue_lock);
```

Two workers read the same `next_task` before either increments, both take the
same job, and one result overwrites the other. The claim must be read *and*
incremented inside one critical section — that is what "atomic" means here.

### Forgetting the `slot >= TASKS` check

Without it, a worker that sees a drained queue still indexes `result[8]`, writing
past the array. The check happens after the unlock, which is fine because `slot`
is a local copy taken under the lock.

### Using `pthread_cond_wait` when a busy check is enough

A real pool blocks on a condition variable when the queue is empty instead of
spinning. This program's queue is fixed and finite, so the worker can exit when
drained. Adding a condition variable to a fixed queue is complexity with no
benefit; adding it to an unbounded one is required.

### Shrinking the pool to the number of tasks

`WORKERS 8, TASKS 8` looks tidier and is worse: you get no benefit from the pool
and one thread per task. The pool should be sized to the number of cores you want
to occupy, not to the workload.
