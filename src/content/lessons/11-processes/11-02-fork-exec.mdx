## Two calls, one pattern

Module 11-01 gave you `fork`, which clones the running program. That is not how a
shell starts `ls` — a clone of the shell would still be the shell. The second
half is `exec`: a family of calls that replace the current program with a
different one, in the same process.

| Call | Effect | Return |
| --- | --- | --- |
| `fork()` | duplicate the process | twice, with 0 in the child |
| `execv(path, argv)` | replace this process's memory with `path` | only on failure, `-1` |

`execv` does not create a process. It overwrites the current one. The PID stays
the same, the open file descriptors survive (unless marked close-on-exec), and
the code that called `execv` is gone. **If `execv` returns, it failed.** There is
no success return, which is why the call is always followed by an error handler.

Combine them and you get the shell's entire mechanism: fork a copy, exec the
program in the child, wait in the parent.

## What you'll be able to do

- Explain what `execv` replaces, and what survives the replacement.
- Say why a call to `execv` that returns is always a failure.
- Build the NULL-terminated `argv` array `execv` requires.
- Read a child's exit status out of `waitpid` with `WEXITSTATUS`.

<TheoryBlock label="Why it matters for C" title="Your argv is a NULL-terminated array of pointers">

	`execv` takes `char *const argv[]`, and the array must end with `NULL` — the callee has no other
	way to know its length. Omitting the terminator means `execv` reads past your array until it
	happens to find a zero. Every `main(int argc, char **argv)` you have ever written received an
	array built exactly this way.
</TheoryBlock>

## Replacing the running image

```c
#define _POSIX_C_SOURCE 200809L

#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    }

    if (pid == 0) {
        /* This process image is replaced entirely by /bin/echo.
           If execv succeeds, nothing below it ever runs. */
        char *args[] = { "echo", "hello from the replaced image", NULL };
        execv("/bin/echo", args);

        /* Reaching this line means exec failed. */
        perror("execv");
        _exit(127);
    }

    int status = 0;
    if (waitpid(pid, &status, 0) < 0) {
        perror("waitpid");
        return 1;
    }

    if (WIFEXITED(status)) {
        printf("the child exited normally with status %d\n",
               WEXITSTATUS(status));
    }
    return 0;
}
```

Two details in that listing are load-bearing.

`args[0]` is `"echo"`, not the full path. By convention `argv[0]` is the program
name as invoked, and many programs use it in their error messages. The path goes
to `execv` separately.

The child uses `_exit(127)`, not `exit(127)`. `_exit` skips the atexit handlers
and, crucially, does not flush stdio buffers that are already shared with the
parent. Calling `exit` here after a failed exec can duplicate buffered output.

`fork()` and `execv()` are POSIX. **`fork()` does not exist on Windows**, and
neither does the fork-then-exec pattern, because Windows cannot duplicate a
running process — `CreateProcess` takes an executable path and builds a new
process around it. Portable code that needs both steps either wraps them in a
library or uses `posix_spawn`, a single call designed for exactly the cases where
the two-step dance is unnecessary.

## Expected output

```text
hello from the replaced image
the child exited normally with status 0
```

`/bin/echo` printed the first line, not your program. That is the proof the
image was replaced. The second line is your parent, which never ran `execv` and
is still the original program.

If you changed the path to something that does not exist, `execv` would return
`-1`, `perror` would print the reason, and `_exit(127)` would make the parent
report status 127. That convention — 127 for "could not run the command" — is
why a shell tells you a command was not found.

## Common pitfalls

### Putting code after `execv` and expecting it to run

On success, the process image is gone. Statements after `execv` only execute when
it fails. Code that assumes otherwise — a cleanup function, a closing `printf` —
silently never runs. If you need cleanup in the child on the success path, use
`atexit` *before* the exec, or accept that the new program owns the process now.

### Forgetting `NULL` in the argv array

```c
char *args[] = { "echo", "hi" };   /* no terminator */
```

This compiles. It is undefined behaviour at runtime: `execv` scans past the array.
If it does not crash, it may pass a garbage pointer as `argv[2]`. Always end with
`NULL`, and let the compiler's `-Wsentinel`-style checks help where they can.

### Using `exit` instead of `_exit` in the child

After `fork`, the child holds a copy of the parent's stdio buffer. `exit` flushes
it, so buffered output can appear twice. `_exit` does not flush. In a child that
is about to `exec` or has failed to, `_exit` is the correct call.

### Treating a returned `execv` as success

`execv` has no success return. Any return at all is a failure. Writing
`if (execv(path, args) == 0) { /* worked */ }` is dead code with a misleading
shape; write the error path unconditionally after the call.
