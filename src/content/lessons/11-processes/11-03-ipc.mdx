## Separate memory means separate everything

Module 11-01 established that `fork` copies the address space. That is a
protection win and a communication problem: a child that computes an answer has
no way to hand it back through a variable. The kernel provides channels for
exactly this, and the lecture calls them **inter-process communication** (IPC).

The mechanisms, roughly in order of cost:

| Mechanism | Scope | Data copied? | Typical use |
| --- | --- | --- | --- |
| pipe | related processes | yes, through the kernel | shell pipelines |
| FIFO (named pipe) | any processes | yes | simple daemons |
| shared memory | any processes | no — mapped into both | highest throughput |
| socket | same or different machines | yes | networks, Lecture 20 |
| signal | any | one integer, no payload | notification, not data |

Shared memory is fastest because it copies nothing: both processes map the same
physical pages. Everything else goes through the kernel, which is correct and
slower. That trade is the whole design space.

## What you'll be able to do

- Name the five IPC mechanisms and the cost trade between them.
- Explain why shared memory is fastest and when that speed is a trap.
- Create a pipe, close the unused ends, and say what happens if you do not.
- Read a byte stream and place the terminator `read` will not give you.

<TheoryBlock label="Why it matters for C" title="A pipe is two file descriptors, and descriptors are inherited">

	`pipe()` fills a two-element array: `fds[0]` is the read end, `fds[1]` is the write end. Both are
	ordinary descriptors — you can `read` and `write` them, and they survive `exec`. That last fact is
	why `ls | grep txt` works: the shell builds the pipe, then execs both programs with the
	descriptors already in place.
</TheoryBlock>

## A pipe between a parent and its child

```c
#define _POSIX_C_SOURCE 200809L

#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fds[2];
    if (pipe(fds) != 0) {
        perror("pipe");
        return 1;
    }

    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    }

    if (pid == 0) {
        /* Child writes. It never needs the read end, so close it —
           otherwise the reader would never see end-of-file. */
        close(fds[0]);

        const char *msg = "42 degrees";
        ssize_t n = write(fds[1], msg, strlen(msg));
        if (n < 0) {
            perror("write");
            _exit(1);
        }
        close(fds[1]);
        _exit(0);
    }

    /* Parent reads. */
    close(fds[1]);

    char buf[64];
    ssize_t n = read(fds[0], buf, sizeof buf - 1);
    if (n < 0) {
        perror("read");
        return 1;
    }
    buf[n] = '\0';

    printf("parent received %zd bytes: %s\n", n, buf);

    close(fds[0]);
    if (waitpid(pid, NULL, 0) < 0) {
        perror("waitpid");
        return 1;
    }
    return 0;
}
```

The two `close` calls are not tidiness. Each process closes the end it does not
use, so that when the writer finishes, every write end is closed and the reader
sees end-of-file. Leave the parent's copy of `fds[1]` open and the parent's
`read` blocks forever waiting for a writer that is really itself.

`buf[n] = '\0'` is also mandatory. `read` does not terminate the data — it gives
you bytes. Every string operation after it needs a terminator you placed.

`pipe()`, `fork()`, `read()`, and `waitpid()` are POSIX. **`fork()` does not
exist on Windows**, and neither do anonymous pipes created this way; Windows has
`CreatePipe` plus `ReadFile` on a pair of handles. The idea transfers — a
kernel-owned channel between two processes — but not one line of the code.

## Expected output

```text
parent received 10 bytes: 42 degrees
```

Ten is `strlen("42 degrees")`. The child wrote exactly those bytes and closed its
end; the parent's `read` returned 10, not 64, because a pipe read returns what is
available.

If the child had written 100 bytes, the parent's single `read` with a 63-byte
buffer would return 63 and the rest would still be in the pipe. A pipe is a byte
stream, not a message queue — the boundary between writes is not preserved. Code
that needs messages has to frame them itself: a length prefix, or a delimiter,
and a loop.

## Common pitfalls

### Leaving the write end open and hanging forever

The reader blocks until every write descriptor is closed. `fork` duplicates the
descriptors, so both processes hold both ends. Close the unused end in each, and
close the write end when done. A hang in pipe code is almost always an
unclosed descriptor, not a slow writer.

### Assuming one `read` gets one `write`

Pipes do not preserve write boundaries, and a single read may return less than
was written — or, if the writer wrote twice quickly, the concatenation of both.
Never parse a pipe as though each `read` were a message. Read until a delimiter
or a known length.

### Writing more than the pipe buffer can hold

A pipe holds a bounded number of bytes (`PIPE_BUF` is at least 512 on POSIX).
Writing far more than that with no reader blocks until space frees up. If both
processes write before either reads, and the buffer fills, both block forever.
That is a deadlock, and module 15 gives it a name.

### Using a pipe between unrelated processes

An anonymous pipe only exists in the processes that inherited it through `fork`.
Two programs started separately cannot open one. That is what a named pipe
(`mkfifo`) or a socket is for.
