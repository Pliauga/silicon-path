## Two behaviours, one address space

RAM and ROM are not different wires. They are different *answers* to the
question "what happens when the CPU writes here". RAM accepts the write
and remembers it; ROM refuses, or accepts nothing. From the CPU's point
of view both are addresses it can read, and the distinction lives in a
permission attached to a region, not in a separate instruction.

**RAM** — random-access memory — is read-write and loses its contents
when power goes away. That last property is why a program starts from
zeroes and not from the values the last program left behind.

**ROM** — read-only memory — is written once, at manufacture or at
firmware-flash time, and read thereafter. The boot code that runs before
anything else is stored this way so it cannot be accidentally
overwritten by the very software it is loading.

## What you'll be able to do

- Explain the difference between RAM and ROM in terms of a permission bit.
- Describe why a boot ROM must be read-only.
- Model an address space with mixed permissions in C.
- Say what `volatile` does to a compiler's assumptions about a location.

## The map, not the memory

A real machine's address space is a table of regions, each with a purpose
and a set of permissions. The program below models a deliberately tiny
one: 64 bytes, four regions of 16, two writable and two read-only.

| Region       | Kind | Writable | Why |
| ------------ | ---- | -------- | --- |
| boot ROM     | ROM  | no       | the code that loads everything else |
| kernel RAM   | RAM  | yes      | the OS's own working memory |
| data RAM     | RAM  | yes      | the program's heap and stack |
| device space | ROM  | no       | registers belonging to hardware |

The interesting row is the last one. Device registers are read-write in
principle, but they are not *this program's* memory, so treating them as
ordinary writable addresses is how a driver ends up corrupting a
controller. The model marks the region read-only to make the point that
permission is a property of the region, not of the bytes.

<TheoryBlock label="Why it matters for C" title="A pointer does not know what it points at">

	C's type system tells you the shape of the value at an address, never
	whether writing there is legal. `*(volatile uint32_t *)0x40000000 = 1;`
	compiles cleanly and does something entirely different on a machine
	where that address is a ROM. On a desktop the operating system stops
	you with a segmentation fault; on a microcontroller there may be no
	such protection and the write simply does nothing, silently.
</TheoryBlock>

## Modelling the regions

The write function is the whole lesson: check the region, refuse or
accept, and report which. Reads are unguarded because reading a ROM is
exactly what it is for.

```c
#include <stdint.h>
#include <stdio.h>

/* A 64-byte toy address space split into four regions. The point is not
 * that a PC works this way in detail, but that the two kinds of memory
 * differ by a permission bit, not by a wire. */

#define SPACE 64u
#define REGION 16u

enum kind { RAM, ROM };

struct region {
    const char *name;
    enum kind kind;
};

static const struct region MAP[SPACE / REGION] = {
    {"boot ROM", ROM},
    {"kernel RAM", RAM},
    {"data RAM", RAM},
    {"device space", ROM},
};

static uint8_t bytes[SPACE];

static int write_byte(uint8_t addr, uint8_t value) {
    if (addr >= SPACE) {
        printf("  write 0x%02X: out of range\n", (unsigned)addr);
        return 0;
    }
    unsigned r = addr / REGION;
    if (MAP[r].kind == ROM) {
        printf("  write 0x%02X: refused, %s is read-only\n",
               (unsigned)addr, MAP[r].name);
        return 0;
    }
    bytes[addr] = value;
    return 1;
}

static uint8_t read_byte(uint8_t addr) {
    return (addr < SPACE) ? bytes[addr] : 0u;
}

int main(void) {
    printf("address space: %u bytes in %u regions of %u\n\n",
           SPACE, SPACE / REGION, REGION);

    printf("region map:\n");
    for (unsigned r = 0; r < SPACE / REGION; r++) {
        printf("  0x%02X-0x%02X  %-13s %s\n",
               r * REGION, r * REGION + REGION - 1,
               MAP[r].name, MAP[r].kind == RAM ? "writable" : "read-only");
    }

    printf("\nprobing writes:\n");
    unsigned accepted = 0;
    for (unsigned a = 0; a < SPACE; a += REGION / 2u) {
        accepted += (unsigned)write_byte((uint8_t)a, (uint8_t)(a + 1u));
    }

    printf("\naccepted %u of %u writes\n", accepted, SPACE / (REGION / 2u));

    /* Volatile: the boot vector is not a variable, it is an address that
     * something outside this program may change. */
    volatile uint8_t *const boot_vector = &bytes[0];
    printf("boot byte after all writes: 0x%02X\n", read_byte(0));
    printf("boot vector still reads:    0x%02X\n", (unsigned)*boot_vector);

    /* A ROM byte that was never written is whatever the manufacturer
     * burned in. Here it is zero, because this array starts zeroed. */
    size_t nonzero = 0;
    for (unsigned a = 0; a < REGION; a++) {
        if (read_byte((uint8_t)a) != 0u) {
            nonzero++;
        }
    }
    printf("boot ROM bytes that changed: %zu\n", nonzero);
    return 0;
}
```

## Expected output

```text
address space: 64 bytes in 4 regions of 16

region map:
  0x00-0x0F  boot ROM      read-only
  0x10-0x1F  kernel RAM    writable
  0x20-0x2F  data RAM      writable
  0x30-0x3F  device space  read-only

probing writes:
  write 0x00: refused, boot ROM is read-only
  write 0x08: refused, boot ROM is read-only
  write 0x30: refused, device space is read-only
  write 0x38: refused, device space is read-only

accepted 4 of 8 writes
boot byte after all writes: 0x00
boot vector still reads:    0x00
boot ROM bytes that changed: 0
```

Four writes were refused and four accepted, one pair per region, because
the probe steps by eight through a 64-byte space. The last three lines
are the point: after a full sweep of attempted writes, the boot ROM is
byte-for-byte unchanged. A refused write leaves no trace — which is
exactly the behaviour you want from firmware and exactly the behaviour
that makes a driver bug so hard to see.

## Common pitfalls

### Expecting `volatile` to make memory safe

`volatile` tells the compiler "do not cache this value in a register;
re-read it every time". It says nothing about whether the address is
writable, and it does not make an operation atomic. It is the right tool
for a device register and the wrong tool for a shared counter between
threads.

### Assuming uninitialised memory is zero

Global and static arrays are zero-initialised by the C standard; local
arrays are not. The `bytes` array in the program above is `static`, which
is why it starts at zero and why "the boot ROM holds zeroes" is true here.
A local `uint8_t buf[64];` holds whatever was on the stack.

### Treating a ROM address as constant across machines

The address of a boot vector is a property of the machine's memory map,
not of C. Code that hardcodes `0xFFFF0000` is correct on one board and
meaningless on another. Portable code gets these addresses from a header
the platform provides.
