## Three states, forever

The processor's life is a loop with three beats. It reads the instruction
the program counter points at — **fetch**. It works out what that
instruction means — **decode**. It does it — **execute**. Then it does the
whole thing again, ten million times a second on the machine you are
reading this on.

Everything else in this module is an optimisation on that loop. The
states themselves do not change, and that is the point: a CPU is a state
machine with three states and a counter.

## What you'll be able to do

- Model a CPU as a state machine over an instruction array.
- Trace a program's execution one cycle at a time.
- Explain why a jump makes the cycle count data-dependent.
- Say what the program counter holds during each state.

## The loop, precisely

| State   | Reads              | Writes              | Advances PC? |
| ------- | ------------------ | ------------------- | ------------ |
| fetch   | memory at `pc`     | instruction register | no          |
| decode  | instruction register | control signals    | no           |
| execute | registers, memory  | registers, memory   | yes          |

The program counter does not move during fetch. That surprises people:
fetch *reads* from `pc`, it does not increment it. The increment happens
in execute, alongside the instruction's real work, so that a jump can
overwrite the counter before it is ever incremented. Do it in the wrong
order and every jump lands one instruction too far.

<TheoryBlock label="Why it matters for C" title="A loop costs what its branches say">

	The cycle count of a C loop is not a property of the loop's body. It is
	the body plus the compare and the branch, and on a modern core the
	branch is often free while the compare is not. This is why a `for` loop
	over an array and a `while` loop with an index can differ by 30% on the
	same data — the compiler turns one into a pointer walk and leaves the
	other with an explicit counter.
</TheoryBlock>

## A machine you can single-step

The program below is a complete CPU for a six-instruction language. It
has an accumulator, eight words of memory, and a program that adds two
numbers and then counts down to zero with a conditional jump.

```c
#include <stdint.h>
#include <stdio.h>

/* A fetch-decode-execute machine over a fixed instruction array.
 * Three states, one cycle function, and a program counter that can move
 * backwards when a jump says so. That is the whole CPU model. */

enum { FETCH, DECODE, EXECUTE, HALTED };
static const char *const STATE_NAME[] = {"FETCH", "DECODE", "EXECUTE", "HALTED"};

enum opcode { LD = 0, ST, ADD, SUB, JNZ, HLT };
static const char *const OP_NAME[] = {"LD", "ST", "ADD", "SUB", "JNZ", "HLT"};

struct instr {
    uint8_t op;
    uint8_t arg;  /* memory address, or jump target for JNZ */
};

struct cpu {
    int state;
    unsigned pc;
    int acc;
    unsigned cycles;
    int memory[8];
};

/* acc = 1 + 2, then subtract 1 until acc is zero, store it, halt.
 *   0 LD 0     acc = mem[0]      (1)
 *   1 ADD 1    acc += mem[1]     (2 -> 3)
 *   2 SUB 2    acc -= mem[2]     (-1 each pass)
 *   3 JNZ 2    if acc != 0, jump back to 2
 *   4 ST 3     mem[3] = acc
 *   5 HLT */
static const struct instr PROGRAM[] = {
    {LD, 0}, {ADD, 1}, {SUB, 2}, {JNZ, 2}, {ST, 3}, {HLT, 0},
};
#define PROGRAM_LEN (sizeof PROGRAM / sizeof PROGRAM[0])

/* Run exactly one cycle. Returns the instruction executed this cycle, or
 * NULL for the fetch and decode cycles that produce no visible change. */
static const struct instr *cycle(struct cpu *c) {
    c->cycles++;
    switch (c->state) {
    case FETCH:
        c->state = (c->pc < PROGRAM_LEN) ? DECODE : HALTED;
        return NULL;
    case DECODE:
        c->state = EXECUTE;
        return NULL;
    case EXECUTE: {
        const struct instr *in = &PROGRAM[c->pc];
        c->pc++;
        switch (in->op) {
        case LD:  c->acc = c->memory[in->arg];  break;
        case ST:  c->memory[in->arg] = c->acc;  break;
        case ADD: c->acc += c->memory[in->arg]; break;
        case SUB: c->acc -= c->memory[in->arg]; break;
        case JNZ: if (c->acc != 0) { c->pc = in->arg; } break;
        case HLT: c->state = HALTED; return in;
        }
        c->state = FETCH;
        return in;
    }
    default:
        return NULL;
    }
}

int main(void) {
    struct cpu cpu = {FETCH, 0, 0, 0, {1, 2, 1, 0, 0, 0, 0, 0}};

    /* The first instruction, one state per line: this is the cycle the
     * deck draws. */
    printf("one instruction, three cycles:\n");
    printf("  %-8s pc=%u acc=%d\n", STATE_NAME[cpu.state], cpu.pc, cpu.acc);
    cycle(&cpu);
    printf("  %-8s pc=%u acc=%d\n", STATE_NAME[cpu.state], cpu.pc, cpu.acc);
    cycle(&cpu);
    printf("  %-8s pc=%u acc=%d\n", STATE_NAME[cpu.state], cpu.pc, cpu.acc);

    /* The rest, one line per executed instruction. */
    printf("\n%-6s %-6s %-4s %-5s %-5s %s\n",
           "cycle", "instr", "pc", "acc", "arg", "effect");
    unsigned executed = 1;

    for (unsigned guard = 0; guard < 200 && cpu.state != HALTED; guard++) {
        const struct instr *in = cycle(&cpu);
        if (in == NULL) {
            continue;
        }
        executed++;
        const char *effect = "";
        if (in->op == JNZ) {
            effect = (cpu.acc != 0) ? "jumped back" : "fell through";
        } else if (in->op == ST) {
            effect = "memory written";
        } else if (in->op == HLT) {
            effect = "stopped the clock";
        }
        printf("%-6u %-6s %-4u %-5d %u", cpu.cycles,
               OP_NAME[in->op], cpu.pc, cpu.acc, (unsigned)in->arg);
        if (effect[0] != '\0') {
            printf("    %s", effect);
        }
        putchar('\n');
    }

    printf("\nhalted after %u cycles, %u instructions executed\n",
           cpu.cycles, executed);
    printf("acc = %d, mem[3] = %d\n", cpu.acc, cpu.memory[3]);
    printf("cycles per instruction: %.2f\n",
           (double)cpu.cycles / (double)executed);
    return 0;
}
```


The `pc` column is the counter *after* the instruction ran, which is why
the last line shows 6 — one past the end of a six-instruction program.

The interesting number is `cycles per instruction: 2.73`, not 3. Two
instructions in this run were wasted on fetch cycles that discovered the
end of the program. In a longer program the ratio converges on exactly
three, and a real processor gets it closer to one by overlapping the
stages — which is the next lesson.

`acc = 0, mem[3] = 0` confirms the countdown worked: 3, 2, 1, then zero,
and the store happened after the loop exited.

## Common pitfalls

### Incrementing the program counter during fetch

If fetch does `c->pc++`, a jump instruction that overwrites `pc` in
execute has already had its target incremented. The program runs one
instruction past every jump target, which looks like a subtle arithmetic
bug rather than a control bug. Increment in execute, after the jump has
had its chance.

### Forgetting the halt state

Without a `HLT`, a program that runs off the end of the array reads
whatever follows in memory. The model above checks `pc < PROGRAM_LEN`
during fetch and halts. Real machines have no such check — they execute
whatever bytes are at that address, which is how a bad jump corrupts a
program in ways that look like data errors.

### Counting cycles as three per instruction

It is three only when nothing goes wrong. Fetching past the end, a
branch, and a cache miss all add cycles. The `2.73` above is not a bug in
the division; it is what an honest cycle count looks like on a short
program.

### Confusing the accumulator with memory

`acc` is a register — one value inside the CPU. `memory` is an array
outside it. `LD` copies memory into the accumulator, `ST` copies back.
Forgetting the distinction makes `LD 0` look like it should change
`mem[0]`, which it never does.
