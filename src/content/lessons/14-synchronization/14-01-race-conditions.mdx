## Three steps wearing one disguise

`counter++` looks like one operation. It is three: load `counter` from memory
into a register, add one to the register, store the register back to memory.
Between the load and the store, another thread can run the same three steps on
the same address, and one of the two updates disappears.

That window is the whole problem. A **race condition** is a program whose result
depends on the order in which concurrent operations happen to interleave — and
the interleaving is chosen by the scheduler, the cache, and the phase of the
moon. Nothing in the C standard forbids any ordering, so any ordering that
loses an update is a legal execution.

The **critical section** is the span of code that must not interleave: the load,
the add, and the store, all three. Protecting two of them is not protecting the
section.

## What you'll be able to do

- Break `counter++` into its three steps and name the window between them.
- Define a race condition and a critical section in terms of that window.
- Explain why `volatile` does not fix a lost update.
- Recognise a lost-update bug by its symptom rather than by a crash.

<TheoryBlock label="Why it matters for C" title="The compiler is allowed to surprise you — and it under-reports">

	`counter++` on a plain `long` is undefined behaviour the moment two threads touch it without
	synchronization. Not "unspecified value" — undefined behaviour, which means the optimizer may
	assume it never happens. That is why a racy program can pass on one machine, fail on another, and
	change behaviour when you add a `printf`. It is also why the fix has to be a real primitive
	(mutex, atomic) rather than a `volatile` qualifier, which only stops some caching and provides
	no mutual exclusion at all.
</TheoryBlock>

## The failure, demonstrated

Four threads each increment the same global `long` half a million times. Two
million increments, so the answer should be 2000000.

```c
/* Four threads share one counter, and no lock protects it. */
#include <pthread.h>
#include <stdio.h>

#define THREADS 4
#define ITERATIONS 500000

static long counter = 0;

static void *bump(void *arg) {
    (void)arg;
    for (int i = 0; i < ITERATIONS; i++) {
        counter++;              /* load, add, store — three steps, not one */
    }
    return NULL;
}

int main(void) {
    pthread_t t[THREADS];

    for (int i = 0; i < THREADS; i++) {
        if (pthread_create(&t[i], NULL, bump, NULL) != 0) {
            fprintf(stderr, "could not create thread %d\n", i);
            return 1;
        }
    }
    for (int i = 0; i < THREADS; i++) {
        pthread_join(t[i], NULL);
    }

    printf("counter  = %ld\n", counter);
    printf("expected = %d\n", THREADS * ITERATIONS);
    return 0;
}
```

Pthreads are POSIX, not ISO C. macOS and Linux ship them; Windows does not, so
this program does not build there. Compile with the thread flag and the standard
warning set:

```text
gcc -std=c11 -Wall -Wextra -pthread race.c -o race
./race
```

## Expected output

This program is not deterministic, and that is the point. One run on this machine
printed:

```text
counter  = 555229
expected = 2000000
```

**Your run will print a different number, and it may be lower.** Repeated runs
on this machine landed everywhere between 500470 and 822234 — always under the
expected total, never the same twice — because each core's cache holds its own
copy of `counter` and they overwrite each other in blocks. Run it ten times and
you get ten answers. Run it on a single-core machine and it may well print
2000000, which is the most dangerous outcome of all: the bug is still there and
now you believe it is fixed.

Notice what the program does *not* do. It does not crash. It does not print
garbage. It reports a plausible number slightly lower than expected, which is
exactly the kind of result that survives code review.

## Common pitfalls

### Believing `volatile` fixes it

`volatile` tells the compiler the value may change outside the program's control,
so it cannot keep it in a register across statements. It says nothing about
atomicity, and it does not stop two threads from interleaving their load, add,
and store. Adding `volatile` to `counter` above produces a program that still
loses updates. Mutual exclusion needs a mutex or an atomic type.

### Protecting part of the critical section

Locking the read and unlocking before the write leaves the window open. A common
shape is a lock around a check, then work done outside the lock:

```c
if (count > 0) {              /* check */
    take_from_buffer();       /* use — the buffer may be empty by now */
}
```

The check and the use must be inside the same critical section, or another
thread can slip between them.

### Testing on one core and calling it verified

A single-core machine serializes threads more often, so a racy program can pass
thousands of runs. The C abstract machine has no cores; the race is real on every
conforming implementation. Treat "I could not reproduce it" as no evidence.

### Assuming the lost updates are evenly spread

They are not. The numbers cluster because the cache line ping-pongs in bursts:
one core holds the line for a while, updates freely, then the next core takes it.
The result looks like a plausible throughput measurement, not like corruption,
which is why this bug is found in production rather than in testing.
