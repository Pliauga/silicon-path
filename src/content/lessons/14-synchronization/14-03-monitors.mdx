## The problem with bare mutexes

Last lesson's bounded buffer works, but look at what it asks of the programmer.
Two semaphores count slots and items; a mutex protects the indices; the order in
which you touch them decides whether the program runs or deadlocks. Get the order
right and it works. Get it wrong and it hangs. The correctness lives in your head,
not in the code.

A **monitor** moves that correctness into the code. The idea: a mutex plus one or
more **condition variables**, with one rule — you hold the mutex whenever you
touch the shared data. A condition variable is not a count and holds no value. It
is a waiting room. `pthread_cond_wait(&cv, &mutex)` does three things atomically:
releases the mutex, blocks until signalled, and reacquires the mutex before
returning. That atomicity is the whole point — it closes the window where a
thread releases the lock and another thread signals before the first is asleep.

C has no `monitor` keyword. C++ and Java do. In C the pattern is written by hand,
and this lesson is that pattern.

## What you'll be able to do

- Define a monitor as a mutex plus condition variables and a locking rule.
- Explain what `pthread_cond_wait` does atomically, and why that matters.
- Guard a wait with `while` rather than `if`, and say what breaks otherwise.
- Signal the right condition variable, with the mutex held, after changing state.

<TheoryBlock label="Why it matters for C" title="`while`, never `if`">

	`pthread_cond_wait` can wake up without a signal — a spurious wakeup is permitted by POSIX — and
	another thread can consume the condition between the signal and your thread reacquiring the mutex.
	Both mean the predicate you checked before waiting may be false again when you return. So the wait
	goes inside `while (condition_not_met)`, never `if`. Code that uses `if` compiles, passes tests, and
	fails once a month in production. This is the single most common bug in hand-written monitors.
</TheoryBlock>

## The pattern on a bounded queue

One producer, one consumer, capacity three, six items. The mutex protects `queue`,
`count`, and `handled`. Two condition variables say *"there is room"* and
*"there is something to take"*.

```c
#define _POSIX_C_SOURCE 200809L

#include <pthread.h>
#include <stdio.h>

/* POSIX has no monitor keyword. A monitor is a mutex plus one or more
   condition variables, with the rule that you hold the mutex whenever you
   touch the shared state. This is that pattern on a bounded queue. */

#define CAPACITY 3
#define PRODUCED 6

static int queue[CAPACITY];
static int count = 0;
static int handled = 0;

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;

static void put(int value) {
    pthread_mutex_lock(&lock);
    while (count == CAPACITY) {
        pthread_cond_wait(&not_full, &lock);    /* releases lock while waiting */
    }
    queue[count++] = value;
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&lock);
}

static int take(void) {
    pthread_mutex_lock(&lock);
    while (count == 0) {
        pthread_cond_wait(&not_empty, &lock);
    }
    int value = queue[0];
    for (int i = 1; i < count; i++) {
        queue[i - 1] = queue[i];
    }
    count--;
    handled++;
    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&lock);
    return value;
}

static void *producer(void *arg) {
    (void)arg;
    for (int i = 0; i < PRODUCED; i++) {
        put(i);
    }
    return NULL;
}

static void *consumer(void *arg) {
    (void)arg;
    for (int i = 0; i < PRODUCED; i++) {
        int value = take();
        printf("consumer took %d\n", value);
    }
    return NULL;
}

int main(void) {
    pthread_t prod;
    pthread_t cons;

    if (pthread_create(&prod, NULL, producer, NULL) != 0 ||
        pthread_create(&cons, NULL, consumer, NULL) != 0) {
        fprintf(stderr, "could not create threads\n");
        return 1;
    }

    pthread_join(prod, NULL);
    pthread_join(cons, NULL);

    printf("handled = %d of %d\n", handled, PRODUCED);

    pthread_cond_destroy(&not_full);
    pthread_cond_destroy(&not_empty);
    pthread_mutex_destroy(&lock);
    return 0;
}
```

Three things to notice. `put` and `take` are the *only* functions that touch
`queue`, `count`, or `handled`, and each takes the lock on entry and releases it
on exit — the invariant is enforced at the boundary, which is what a language
monitor does for you automatically. The `while` loops guard the waits. And each
function signals *after* changing the state but *before* releasing the lock,
which is safe because the signaller still holds it.

```text
gcc -std=c11 -Wall -Wextra -pthread monitor.c -o monitor
./monitor
```

## Expected output

```text
consumer took 0
consumer took 1
consumer took 2
consumer took 3
consumer took 4
consumer took 5
handled = 6 of 6
```

Here is the interesting part. With capacity three and six items, the producer
cannot run ahead: it fills three slots, then blocks on `not_full` until the
consumer drains one. Yet the output is fully ordered, `0` through `5`. That is
not luck. The producer is only ever ahead by three items, so the consumer always
takes the oldest item before a newer one can be produced, and a single consumer
thread cannot reorder what it takes. The *timing* varies between runs; the
sequence does not.

Change one thing — two consumers — and the order becomes genuinely
non-deterministic, because either consumer may take the next item. The counts
stay correct and `handled` still reaches 6. That is the invariant the monitor
protects; the order is not part of it.

Windows has neither `<pthread.h>` nor `<semaphore.h>`, so this program is POSIX
only. On Windows the equivalent modern spelling is a `CRITICAL_SECTION` plus
`CONDITION_VARIABLE`, and the `while` rule is identical.

## Common pitfalls

### `if` instead of `while` around the wait

The bug this lesson keeps returning to. Between `pthread_cond_signal` and the
woken thread actually reacquiring the mutex, a third thread can take the item.
The woken thread then proceeds believing there is work when there is none, reads
uninitialised memory, or decrements a count below zero. `while` re-checks and
goes back to sleep.

### Signalling while not holding the lock

POSIX allows it, and it is usually a mistake. The signal can be delivered while
the waiter has not yet called `pthread_cond_wait`, so the wakeup is lost and the
waiter sleeps forever. Signal with the mutex held and the state already updated;
the waiter cannot be between checking the predicate and sleeping, because it
holds the mutex to check.

### Using one condition variable for two conditions

A single `cond` for both "room available" and "item available" means a signal
may wake the wrong kind of waiter, which then re-checks, finds nothing, and sleeps
again — wasteful, and with `pthread_cond_signal` rather than `broadcast` it can
stall entirely. One condition variable per predicate.

### Forgetting that `pthread_cond_wait` takes the mutex by pointer

The second argument must be the same mutex you hold. Passing a different one is
undefined behaviour: the function unlocks that other mutex — which you do not
hold — and your thread continues holding the real one while asleep. The symptom
is a hang with no diagnostic.
