## Where the machines live, and what happens when one stops

Service models describe *who owns which layer*. Deployment models describe
*where the copies are and how they relate*. The four you need are private,
public, hybrid, and community — plus the distinction that matters far more in
practice: single-region versus multi-region, and active-passive versus
active-active.

The distinction that matters is not the label on the contract. It is the
**failure domain**: the set of things that fail together. Two servers in the
same rack share a power supply. Two racks in the same room share a cooling
system. Two rooms in the same city share a power grid and a fibre route. Two
cities do not share those, but they do share a DNS provider, a certificate, and
a deploy pipeline, and those fail too.

## What you'll be able to do

- Distinguish service model from deployment model without conflating them.
- Compute the availability of *n* independent copies and say what "independent" is assuming.
- Identify the shared dependencies that make redundancy fictional.
- Convert a "nines" figure into downtime you can picture.

## The four labels

| Model | Who may use it | Typical reason | Typical problem |
| --- | --- | --- | --- |
| private | one organisation | regulation, data residency, existing hardware | you own every failure |
| public | anyone, multi-tenant | elasticity, no capital cost | noisy neighbours, egress fees |
| hybrid | one organisation, both | keep sensitive data home, burst to public | two of everything to operate |
| community | a defined group | shared cost among similar bodies | governance and shared roadmap |

Hybrid is the most misunderstood. It is not "we use both." It is a specific
architecture with a defined boundary — usually a network link or a replication
channel — and the boundary is where the hard problems live: latency across it,
identity across it, and what happens when it is down. A hybrid deployment whose
link fails in a way that takes the private half down with it has the cost of
both models and the availability of the worse one.

<TheoryBlock label="Why it matters for C" title="'Independent' is a claim about failure, not about geography">

	Two processes on one kernel are not independent: they share the scheduler, the
	page cache, and the OOM killer. Two containers on one host are not independent
	for the same reason. Two hosts in one rack share power. The C programmer's
	version of this lesson is that a mutex protecting a variable in one process
	does nothing for a second process — different address space, different
	assumption, same category of mistake. Redundancy only multiplies reliability
	across a boundary that the failure cannot cross.

</TheoryBlock>

## Nines, as arithmetic

Availability is usually quoted as a percentage, which hides how much time it
actually is. The program below converts each figure into hours per year and
then computes what redundancy buys — and what it does not.

```c
#include <stdint.h>
#include <stdio.h>

/* Failure budgets, computed rather than claimed.
 *
 * A deployment model is mostly a statement about who absorbs a failure and
 * how much of it they can absorb. The two numbers that decide this are the
 * availability you promise and the number of independent things that can
 * fail. Neither is a marketing property, so both are arithmetic here.
 *
 * "nines" is a way of writing downtime: 99.9% allows 43m 12s of downtime a
 * month; 99.99% allows 4m 19s. Whether one machine can deliver a given figure
 * is then a multiplication. */

struct model {
    const char *name;
    int instances;         /* independent copies of the whole service */
    const char *note;
};

static double seconds_per_month(void) {
    /* 365.25 days / 12 = 30.4375 days */
    return 30.4375 * 24.0 * 60.0 * 60.0;
}

/* Availability of n independent copies, each with availability a, when a
 * failure takes one copy out but the others keep serving. */
static double combined(double a, int n) {
    double down = 1.0 - a;
    double all_down = 1.0;
    for (int i = 0; i < n; i++) {
        all_down *= down;
    }
    return 1.0 - all_down;
}

static void print_downtime(const char *label, double availability) {
    double month = seconds_per_month();
    double down = (1.0 - availability) * month;
    double per_year = down * 12.0;

    printf("%-22s %8.5f%%   %10.1f s/month   %9.2f h/year\n",
           label, availability * 100.0, down, per_year / 3600.0);
}

int main(void) {
    const struct model models[] = {
        {"single server",       1, "one machine, one disk"},
        {"warm standby",        2, "second machine, manual failover"},
        {"active-active",       2, "both serving, load balanced"},
        {"multi-region",        3, "three independent regions"},
    };
    const size_t count = sizeof models / sizeof models[0];

    /* A single machine with a realistic annual failure profile. */
    const double one_node = 0.995;

    printf("baseline: one node available %.3f%% of the time\n\n", one_node * 100.0);
    print_downtime("one node", one_node);
    printf("\n");

    printf("%-22s %11s %14s %14s\n", "model", "copies", "availability", "monthly down");
    printf("%-22s %11s %14s %14s\n", "----------------------",
           "-----------", "--------------", "--------------");

    for (size_t i = 0; i < count; i++) {
        double a = combined(one_node, models[i].instances);
        double down = (1.0 - a) * seconds_per_month();
        printf("%-22s %11d %13.5f%% %11.1f s\n",
               models[i].name, models[i].instances, a * 100.0, down);
    }

    /* The catch: independence is an assumption, not a fact. If the copies
     * share a dependency, the failure is not multiplied out at all. */
    printf("\nif the copies are NOT independent:\n");
    for (size_t i = 0; i < count; i++) {
        double down = (1.0 - one_node) * seconds_per_month();
        printf("  %-20s same as one node: %8.1f s/month\n",
               models[i].name, down);
    }

    /* The other catch: correlated failure has a name. */
    printf("\nshared dependencies that defeat redundancy:\n");
    printf("  - one provider, one region, one control plane\n");
    printf("  - one database both copies write to\n");
    printf("  - one DNS record and one certificate\n");
    printf("  - one deploy pipeline that pushes the same bad config\n");

    /* Orders of magnitude for the reader to hold on to. */
    printf("\nnines, in wall-clock terms per year:\n");
    const double levels[] = {0.99, 0.999, 0.9999, 0.99999};
    const char *names[] = {"two nines", "three nines", "four nines", "five nines"};
    for (size_t i = 0; i < 4; i++) {
        double hours = (1.0 - levels[i]) * 365.25 * 24.0;
        printf("  %-12s %.5f%%  ->  %8.2f hours/year  (%6.1f minutes)\n",
               names[i], levels[i] * 100.0, hours, hours * 60.0);
    }

    /* Cost intuition: each nine is roughly an order of magnitude. */
    printf("\nengineer effort per additional nine is superlinear:\n");
    printf("  the second copy is cheap, the tenth is not\n");
    printf("  coordination cost grows with the number of failure domains\n");

    return 0;
}
```

Read the table honestly. `warm standby` and `active-active` show the **same**
number, because this model only counts how many independent copies exist. It
says nothing about how long failover takes or how much data is lost in the
gap — and those are exactly the differences between the two designs. A warm
standby that takes eight minutes to promote costs you eight minutes of downtime
that this arithmetic does not charge for. Models like this are useful for
spotting the shape of a problem, not for promising a number to a customer.

The second block is the one to remember. Multiply the failure rate of three
copies and you get five nines; fail to notice that all three read from one
database, and you have one nine with three times the bill.

## Region, zone, and the shape of a failure

| Boundary | Fails together when | Typical blast radius |
| --- | --- | --- |
| process | the process crashes | one request in flight |
| container | the host's kernel panics | every container on the host |
| host | the hypervisor or PSU fails | every VM on the host |
| availability zone | power or cooling fails | every host in the zone |
| region | a control-plane or network event | every zone in the region |
| provider | an identity or DNS outage | everything you run there |

The right question is not "how many copies do we have" but "what single event
takes out the most copies at once, and what is our procedure when it does."

## Common pitfalls

### Multiplying availabilities that are not independent

`0.995 × 0.995 = 0.990` is the probability that *both* fail, which is only
valid if the failures are unrelated. Two machines in one rack, booted from one
image, configured by one pipeline, are correlated in at least four ways.

### Designing for a nine you cannot measure

If you do not know your current downtime, you cannot claim an improvement.
Instrument first: the measurement is usually more valuable than the target,
because it reveals which failure actually happens most.

### Treating failover as a document

A failover procedure that has never been executed is a hypothesis. The only
evidence that a standby works is a drill in which the primary was actually
stopped, at a time nobody chose, and the service came back.

### Confusing durability with availability

Availability is whether the service answers now. Durability is whether the data
still exists tomorrow. A single node with hourly snapshots to another region is
highly durable and barely available; three replicas in one zone are the
opposite. They are different budgets and are spent separately.
