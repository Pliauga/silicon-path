## Renting a layer instead of owning a rack

"Cloud" is not a technology. It is a change in who owns each layer of the stack
you learned in module 20, and a change in how you pay for it. When you run a
server yourself you own all seven layers — the cable, the switch, the
virtualisation, the operating system, the runtime, the application. When you
rent a virtual machine you own from the operating system upward and someone
else owns everything below. When you rent a managed database you own the schema
and the queries and nothing else.

The question that decides the model is never "which is modern." It is: **which
layers do we have a reason to control?** Control costs money and, more
importantly, it costs attention. Every layer you own is a layer you patch, a
layer whose release notes you read, and a layer that can page you at 3am.

## What you'll be able to do

- Place IaaS, PaaS, and SaaS on the layer stack and say what each one hands you.
- Compute the total cost of a deployment including staff time, not just the invoice.
- Explain why a managed service can be cheaper and more expensive at the same time.
- Recognise when a service model is the wrong fit for a workload.

## The three models on the stack

| Layer | On-premises | IaaS | PaaS | SaaS |
| --- | --- | --- | --- | --- |
| application | you | you | you | provider |
| runtime / libraries | you | you | provider | provider |
| operating system | you | you | provider | provider |
| virtualisation | you | provider | provider | provider |
| servers, storage, network | you | provider | provider | provider |
| physical facility | you | provider | provider | provider |

The boundary is the contract. In IaaS you get a machine and root on it, which
means you also get every patch Tuesday. In PaaS you get a runtime that accepts
your code and the provider handles the OS, which means you also get the
provider's supported language versions and no ability to install a kernel
module. In SaaS you get a URL and a login, which means you get the provider's
feature roadmap and nothing else.

That trade is not free in either direction. A team that genuinely needs a
custom kernel cannot use PaaS at any price. A team whose product is a CRUD
application and who hand-patches an OS every month is spending its scarcest
resource on its least differentiating work.

<TheoryBlock label="Why it matters for C" title="The layer boundary is a syscall boundary">

	When your C program calls `write()`, it enters the kernel. In every service
	model that kernel is still there and still has the same interface — which is
	why a program compiled for Linux runs unchanged on a rented Linux VM, in a
	container, and inside a PaaS runtime built on that same kernel. What changes
	is who is responsible for patching it. Portability of C across cloud providers
	is real precisely because the syscall interface is not part of anyone's
	product.

</TheoryBlock>

## The cost is mostly people

The invoice from a cloud provider is the visible number and usually the smaller
one. The model below makes the invisible number explicit: staff hours to keep
each layer running. The figures are assumptions, written into the source so you
can disagree with them and rerun.

```c
#include <stdio.h>

/* A cost model, not a quote. Every number below is an assumption written
 * down so the arithmetic can be checked; the point is the shape of the
 * comparison, not the dollar figures.
 *
 * The five columns are the five things you pay for at each service model.
 * The only column that moves is "operations": the hours a person spends
 * patching an OS, tuning a database, or reading release notes. */

struct model {
    const char *name;
    double hardware;      /* amortised server + network, per month */
    double licence;       /* OS, database, middleware */
    double operations;    /* staff hours at a loaded rate */
    double engineer_days; /* your team's time on undifferentiated work */
};

static double monthly_total(const struct model *m) {
    return m->hardware + m->licence + m->operations;
}

int main(void) {
    const struct model models[] = {
        /* name          hardware  licence  ops    eng-days */
        {"on-premises",    820.0,   640.0,  2400.0,   9.0},
        {"IaaS",           900.0,   610.0,  1500.0,   6.5},
        {"containers",     980.0,   380.0,   900.0,   4.0},
        {"PaaS",          1050.0,     0.0,   420.0,   2.0},
        {"SaaS",             0.0,  1400.0,    60.0,   0.5},
    };
    const size_t count = sizeof models / sizeof models[0];

    printf("%-13s %10s %9s %10s %12s %10s\n",
           "model", "hardware", "licence", "operations", "total/month", "eng-days");
    printf("%-13s %10s %9s %10s %12s %10s\n",
           "-------------", "----------", "---------", "----------",
           "------------", "----------");

    double base = monthly_total(&models[0]);

    for (size_t i = 0; i < count; i++) {
        printf("%-13s %10.0f %9.0f %10.0f %12.0f %10.1f\n",
               models[i].name,
               models[i].hardware,
               models[i].licence,
               models[i].operations,
               monthly_total(&models[i]),
               models[i].engineer_days);
    }

    printf("\nchange against on-premises (%.0f/month):\n", base);
    for (size_t i = 0; i < count; i++) {
        double delta = monthly_total(&models[i]) - base;
        double pct = base > 0 ? (delta / base) * 100.0 : 0.0;
        printf("  %-13s %+8.0f  (%+.1f%%)\n", models[i].name, delta, pct);
    }

    /* The interesting column is not the total; it is the fraction of the
     * bill that is a person rather than a machine. */
    printf("\nshare of the bill that is staff time:\n");
    for (size_t i = 0; i < count; i++) {
        double total = monthly_total(&models[i]);
        double staff = total > 0 ? (models[i].operations / total) * 100.0 : 0.0;
        printf("  %-13s %5.1f%%\n", models[i].name, staff);
    }

    /* Break-even: how many months before the difference in engineer-days
     * is worth more than the difference in cash? 8 hours a day, 120/hour. */
    printf("\ncash vs time, against on-premises (a day = 960 in loaded cost):\n");
    for (size_t i = 1; i < count; i++) {
        double cash = monthly_total(&models[i]) - base;
        double days_saved = models[0].engineer_days - models[i].engineer_days;
        double time_saved = days_saved * 960.0;
        printf("  %-13s %+7.0f cash, %+5.1f days saved (%+7.0f value)\n",
               models[i].name, cash, days_saved, time_saved);
    }

    return 0;
}
```

Two things are worth extracting. First, the hardware column barely moves —
between 820 and 1,050 a month. The migration from owning a rack to renting a
managed platform saves almost nothing on hardware and almost everything on
labour. Second, the fraction of the bill that is a person falls from 62% to 4%
across the table. That shift, not the invoice, is what cloud computing changed.

**These numbers are illustrative.** They are a spreadsheet with a compile
step, and the assumptions are ordinary small-business ones. Run them with your
own loaded hourly rate before quoting them at anyone.

## The costs that do not appear in the table

| Hidden cost | Where it lands |
| --- | --- |
| egress bandwidth | usually the largest surprise on a cloud bill |
| vendor lock-in | migrating a managed database can cost more than it saved |
| cold starts | managed runtimes idle out; the first request pays |
| per-request pricing | fine at 10 req/s, alarming at 10,000 |
| compliance scope | a provider's audit does not cover your configuration |

The last row matters more than it looks. A provider being compliant with a
standard says nothing about whether your deployment of it is. The shared
responsibility model draws the line at the service boundary, and everything
above that line is yours whatever the marketing page says.

## Common pitfalls

### Assuming managed means cheaper

At low volume, a managed service is almost always more expensive than a small
VM. The break-even is in staff time, and a team with spare capacity and no
compliance burden may never reach it. Managed services are bought with money to
save attention; if attention is not the constraint, the trade is bad.

### Forgetting to measure egress

Cloud providers charge very little to accept data and noticeably more to send
it out. A backup strategy that copies a terabyte out nightly every month can
cost more than the compute it protects.

### Treating serverless as a smaller server

Function-as-a-service changes the failure modes: cold starts, per-invocation
limits, no persistent local state, and a hard timeout. Code written for a
long-lived process does not become serverless by being wrapped in a handler.
