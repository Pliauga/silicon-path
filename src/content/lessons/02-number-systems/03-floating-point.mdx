## A float is scientific notation in binary

Self-check: `0.1 + 0.2 == 0.3` is false in almost every language, and the
reason is not a language bug. A `double` holds a *binary* fraction, and
one tenth has no finite binary expansion — just as one third has no finite
decimal expansion. `0.1` is stored as the nearest `double`, `0.2` is
stored as the nearest `double`, and their sum is the nearest `double` to
something that was already slightly wrong.

Every `float` and `double` on essentially every machine follows
**IEEE 754**: a sign bit, a biased exponent, and a fraction. The layout is
fixed, which is why the bit patterns below are the same on your laptop and
on a phone.

## What you'll be able to do

- Break a 32-bit float into sign, exponent, and mantissa bits.
- Explain why `0.1 + 0.2` is not `0.3`, in terms of binary fractions.
- Compare floats using a tolerance instead of `==`, and say what the tolerance means.
- Dump a float's bits with `memcpy` instead of a type-punning pointer cast.

## The layout of a 32-bit float

| Field    | Bits | Position | Meaning |
| -------- | ---- | -------- | ------- |
| Sign     | 1    | 31       | `0` positive, `1` negative |
| Exponent | 8    | 30–23    | power of two, biased by 127 |
| Fraction | 23   | 22–0     | bits after the leading `1.` |

The value is `±1.fraction × 2^(exponent - 127)`. The leading `1` is not
stored, because in normalised form it is always there — a free extra bit
of precision.

`24.5` is `11000.1` in binary, which normalises to `1.10001 × 2^4`. The
exponent field is `4 + 127 = 131`, which is `10000011`. The fraction is
`10001000…` padded to 23 bits. Assembled: `0 10000011 10001000000000000000000`,
or `0x41C40000`.

| Value  | Sign | Exponent | Fraction              | Hex          |
| ------ | ---- | -------- | --------------------- | ------------ |
| `1.0`  | `0`  | `01111111` | `00000000000000000000000` | `0x3F800000` |
| `0.5`  | `0`  | `01111110` | `00000000000000000000000` | `0x3F000000` |
| `24.5` | `0`  | `10000011` | `10001000000000000000000` | `0x41C40000` |
| `-2.0` | `1`  | `10000000` | `00000000000000000000000` | `0xC0000000` |
| `0.1`  | `0`  | `01111011` | `10011001100110011001101` | `0x3DCCCCCD` |

Look at the last row. The fraction `10011001100110011001101` is the binary
expansion of one tenth — `0.0001100110011…` repeating — truncated to 23
bits and rounded. It never terminates, so it never fits, so it is never
exactly one tenth.

## Seeing the encoding

The clearest demonstration of IEEE 754 is not arithmetic — it is copying
the bits out and printing them. `memcpy` into a `uint32_t` does this
without violating the strict aliasing rule, which a pointer cast would.

```c
#include <float.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>

static void print_bits32(uint32_t bits) {
    for (int bit = 31; bit >= 0; bit--) {
        printf("%u", (unsigned)((bits >> bit) & 1u));
        if (bit % 8 == 0 && bit != 0) {
            printf(" ");
        }
    }
}

/* Copying the bytes out is the only portable way to see the encoding.
 * Reinterpreting through a pointer would break the strict aliasing rule. */
static void show(float value) {
    uint32_t bits;
    memcpy(&bits, &value, sizeof bits);
    printf("  %-10.4f  0x%08X  ", (double)value, bits);
    print_bits32(bits);
    printf("\n");
}

int main(void) {
    printf("0.1 + 0.2 = %.17f\n", 0.1 + 0.2);
    printf("0.3       = %.17f\n", 0.3);
    printf("equal?    %s\n\n", (0.1 + 0.2 == 0.3) ? "yes" : "no");

    float a = 0.1f;
    float b = 0.2f;
    printf("in float: a + b == 0.3f ? %s\n", (a + b == 0.3f) ? "yes" : "no");
    printf("FLT_EPSILON = %e\n\n", (double)FLT_EPSILON);

    printf("sign exponent mantissa\n");
    show(1.0f);
    show(0.5f);
    show(24.5f);
    show(-2.0f);
    show(0.1f);
    return 0;
}
```

## Expected output

```text
0.1 + 0.2 = 0.30000000000000004
0.3       = 0.29999999999999999
equal?    no

in float: a + b == 0.3f ? yes
FLT_EPSILON = 1.192093e-07

sign exponent mantissa
  1.0000      0x3F800000  00111111 10000000 00000000 00000000
  0.5000      0x3F000000  00111111 00000000 00000000 00000000
  24.5000     0x41C40000  01000001 11000100 00000000 00000000
  -2.0000     0xC0000000  11000000 00000000 00000000 00000000
  0.1000      0x3DCCCCCD  00111101 11001100 11001100 11001101
```

The first two lines are the whole argument in decimal. The `double`
nearest to `0.1` plus the `double` nearest to `0.2` is not the `double`
nearest to `0.3` — it is one unit in the last place above it.
`%.17f` is used because seventeen significant digits is what it takes to
round-trip a `double` exactly; printing fewer would hide the difference.

The third line is the kind of result that makes people distrust floats
entirely, and it deserves care. In `float`, `0.1f + 0.2f == 0.3f` prints
`yes`. That is not a contradiction of the `double` result — it is the same
rounding happening at a coarser width, where the error lands on the same
representable value as `0.3f`. Fewer bits means fewer distinct values,
which means a wider chance of coincidence.

## Comparing floats

There is no correct universal epsilon. The honest comparison is relative:

```c
#include <math.h>

static int nearly_equal(double a, double b) {
    double diff = fabs(a - b);
    double scale = fmax(fabs(a), fabs(b));
    return diff <= 1e-9 * (scale > 1.0 ? scale : 1.0);
}
```

This says "equal to about nine significant digits", which is a claim you
can defend. `fabs(a - b) < 1e-9` alone is wrong for values around `1e12`,
where the representable gap is already larger than `1e-9` and the test
never passes.

`FLT_EPSILON` and `DBL_EPSILON` are the gaps at `1.0` specifically. They
are useful for reasoning about precision, not as a magic tolerance.

## Common pitfalls

### Type-punning through a pointer

`uint32_t bits = *(uint32_t *)&f;` is undefined behaviour under the strict
aliasing rule, and optimisers do exploit it. `memcpy` is the standard
sanctioned way to reinterpret bytes, and compilers turn it into a single
register move.

### Comparing with `==` after arithmetic

`if (x == 0.1)` after computing `x` is a coin flip. Use a relative
tolerance, or restructure so the comparison happens on integers — money in
pence, time in milliseconds, angles in fixed-point steps.

### Assuming `float` and `double` are interchangeable

`float` has 24 bits of significand, `double` has 53. A `double` literal
like `0.1` is not the same value as `0.1f`; assigning one to the other
rounds. In a long accumulation the difference compounds, which is why
numerical code often uses `double` even when memory looks tight.

### Expecting exact decimal output from `%f`

`printf("%.2f", 2.675)` may print `2.67` rather than `2.68`, because
`2.675` is stored as slightly less than `2.675`. Rounding for display
cannot recover digits that were never stored.
